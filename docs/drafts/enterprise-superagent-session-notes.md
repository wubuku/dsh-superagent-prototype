## 2. BYOM：用户给出的关键语义 `[用户]`

- **用户原话**：「企业员工的机器上运行的 agent 可以加入到协作中；也可以实现 BYOM……必要时人工（企业员工）可介入干预，否则 BYOM 没有意义。」
- **助手理解（待确认）**：BYOM 的价值主张不是「借员工的机器算力」，而是「任务跑到人的环境里，人看得见、接得住」。没有人工介入的 BYOM 只是分布式算力租赁。
- **推论（待确认）**：**执行节点的隔离等级应与它承载的信任等级挂钩**。员工自有笔记本与云端按需沙箱不应是同一种节点。

### 2.1 BYOM 的三件套与隔离三层 `[研究]`

既有的原型研究报告把 BYOM 拆成三个部分，这是后续讨论「谁提供什么」的公共词汇：

| 部分 | 所在位置 | 职责 | 原型现状 |
| --- | --- | --- | --- |
| **大脑** | 云端无状态 Loop + 状态库 | 推进 Agent Loop、保存会话与任务状态、可水平扩展或重启替换 | 只有本地常驻 Session + 本地 SQLite |
| **手** | 员工机器上的 daemon | 真实执行、离线/休眠语义、人工接管入口 | 执行动作存在，**daemon 为零**（不是打折） |
| **治理账本** | 中心 | 授权依据、归属、审批、验收、审计、撤销 | 只有应用内 Ticket/Mandate/Assignment |

> **两种「账」不要混**：这里的**治理账本**属于组织（谁批准、谁验收、谁负责），是 BYOM 三件套的第三件，`[研究]` 原文用「账本」一词；而本文后文反复出现的**编排事实 / 编排存储**（§6.2.0）属于 agent 协作（派给谁、跑到哪、对没对上账）。前者不随租户停用而冻结成只读的技术对象，后者是。为避免歧义，本文一律写「治理账本」与「编排存储」这两个全称，不再单用「账本」。

端侧 daemon 至少要承担五件事：执行本体；离线或休眠语义（让中心能判断「中断待恢复」而不是「卡死」）；**人工接管**；**凭据不进入模型上下文**；出口白名单与可回滚的工作区。员工机器间歇在线，因此任务模型必须允许「**分配 → 掉线 → 待恢复或改派**」。

「隔离」也至少有三层，**不能合并成一个词**：

| 层次 | 定义 | 仅做到哪一步还不够 |
| --- | --- | --- |
| **故障域** | 进程边界 + 资源配额；一个 Worker 崩溃或耗尽资源不拖垮 Router 与其他 Worker | 独立 Session、独立工作目录不够，仍共享进程和内存 |
| **文件与凭据边界** | 独立 OS 账号、容器或 mount，让一个 Worker 读不到另一个的代码与凭据 | 同一 UID 下的不同目录不是安全边界 |
| **租户边界** | 授权链 + 网络出口，保证一个租户的任务不能借用另一个租户的身份或数据 | 应用层 principal 字段不等于网络与凭据隔离 |

**顺序判断（既有研究的结论，助手转述）**：先本机进程/环境隔离，再跨机器；两者共享同一个「**执行节点契约**」——assignment 下发、report 回传、status 查询、cancel。先把契约在本机跑通，再铺到网络与凭据上；反过来做，等于用未定型的契约同时承担网络故障和凭据泄露风险。

**未决（新增 Q-K）**：这三层与「三层承载项目」是**正交**的——BOS 管制度、spring-ai-rag 管认知、BlueCortex 管运行，但**故障域/凭据边界/租户边界不由它们中任何一个负责**，它们属于执行节点（daemon）与 Super-Agent 自身的领域。这是目前唯一一块**完全没有承载者**的能力。

## 3. 用户点的「企业级盲区」及三类系统 `[用户]`

- **用户原话**：「文章漏掉了企业的业务流程（SOP 等）与隐性知识如何沉淀。」
- **(a)** 类 Flowable 的工作流引擎 + Agent-Friendly API；
- **(b)** 承载业务知识（含 agent 捕获梳理的隐性知识）的 RAG / 语义知识库；用户**不同意**归入「记忆系统/模块」；
- **(c)** 协调多 agent 协作的过程上下文状态；用户认可可归入记忆模块——「偏原始、偏短期、与运行过程紧绑、信息与价值密度低」。


本章内容来自既有研究材料 `../../../deepseek-harness/docs/drafts/dsh-superagent-prototype-research.md`，**不是你在本会话提出的**。它们此前没有进入本备忘；本次转述是为了不丢失，并标明它们与本项目的距离。


原报告把「采用时」的职责拆开，并明确这不是原型已实现的机制，而是组织必须自己保留的部分：

| 事项 | 组织决定 | 技术承担 |
| --- | --- | --- |
| 目标与优先级 | 选择工作、排序与资源投入 | 按规则筛选、排队、限流、展示积压；**Router 的调度顺序不构成业务优先级** |
| 请求与授权 | 谁能提出/修改/取消何种工作 | 校验主体与来源、记录 Mandate；**能发起任务 ≠ 能批准一切后续操作** |
| 意见与冲突 | 指定决策者、冲突处理方式 | 保留要求与来源；规则不足时交回负责人；**信息汇总 ≠ 裁决权** |
| 上下文与保密 | 哪些信息可对谁、在哪项工作中使用 | 按范围提供上下文并执行访问控制；**部署共享实例 ≠ 信息共享决策** |
| 交付与责任 | 完成标准、验收人、结果责任 | 提供可审阅成果与证据；**模型报告完成 ≠ 业务验收** |

**为什么这条必须保留**：它给「Super-Agent 能做什么」画了一条不可越过的线。我们的设计越贴近企业，越容易在无意间把「技术可以做的」当成「组织的决定已经做了」。这五条是**验收时的检查清单**，不是功能清单。


原报告的判断：**Mandate 回答「这个外部请求是否允许形成一项工作，以及在什么理由下继续」；DSH Permission Preset / 工具审批回答「Agent 能调用哪些能力，以及具体调用是否需要审批」。** 两者互补，任一方都不能代替另一方；尤其自动处理外部事件时，**事件发送者、仓库/组织规则、任务 Mandate、工具调用授权、操作系统权限**要分别审查。

**与本次讨论的衔接（待确认）**：这正是「调用身份」之外的另一条分层——调用身份回答「谁在调」，Mandate 回答「凭什么调」，工具授权回答「能调到什么」。三者需要分别建模，不能合成一个 `permission` 字段。


原报告对「团队收益」的评价项与反向指标，本备忘不复制全表，只保留一句最容易被忽略的：

> **少发通知不等于减少工作，后台静默执行不等于没有资源成本；Ticket 结束数、PR 数、并行 worker 数都不能当作有效交付。**

若本项目最终需要证明「企业版值得做」，这条会是最先被违反的。


四项结论均来自《Super-agent 设计探索》原文（`[代码]` 指向原文归档）与原型研究材料 `[研究]`。它们不是「文章的实现」，而是文章提出且**实验或内部使用验证过**的设计因素。它们不会因为你选了 BOS/spring-ai-rag/BlueCortex 而消失——相反，它们正是三个承载项目**都不负责**的部分，因此属于 Super-Agent 自己的设计域。每项末尾的「对我们的含义」是 `[助手]` 级别的推断。


文章第 3.2 节：**Router 只负责新任务的冷启动与跨任务协调；已确定归属的后续事件由程序直接发给对应 Worker，不经 Router 转发。** 依据是 Thread 上的订阅关系——「Router 根据 Thread 的初始事件创建 Worker 后，该 Worker 直接订阅该 Thread」。文中消融实验显示：去掉直通后完成时间基本不变，但 Router 决定数增加约 30%、读缓存 token 从 2323 万增至 3177 万（+37%）。**结论：直通不改善质量，但显著节省 Router 的开销。**

**对我们的含义（待确认）**：这是**路由成本**问题，与三个承载项目无关。BOS 的 MCP 调用是「谁调谁付」，若每个后续事件都经 Router，Router 会成为企业级规模下的单点费用与延迟源。原型实现了同一机制（Thread 订阅 + Intake 扇出），可直接借鉴其领域模型。


文章第 3.1 节：环境事件流是「高噪音、低触发率」；把明确且稳定的高频判断固化为**确定性代码**（Fast Path），只把需要语义理解的事件交给模型（Slow Path）。原型的对应实现是 Policy gate（纯函数、不调模型）。

**对我们的含义**：企业级来源更多（H1），噪音比更高。**没有确定性前置过滤的 Super-Agent 会在第一步就被成本与延迟击穿。** 这条与「调用身份」「Mandate」共同构成准入链，但它是**性能前提**，不是授权前提。


文章第 4.1 节：把耗时的工具调用改为 `start()` / `stop()`，模型不等工具完成就能响应新消息；并注明「这一异步任务机制**已经在 DeepSeek Harness 中实现，但尚未默认开启**」。

**对我们的含义**：这是三类事实之外的一条**交互前提**——如果执行节点的调用是同步阻塞的，那么「人可随时介入」（BYOM 的意义所在）在技术上不可能。原型的对应做法是「前台命令 5 秒转后台作业」，它是这个机制的一种粗糙近似。


文章第 3.4 节：在结果未必被采用时，Agent 先于后台尝试；有价值则交付，无价值则丢弃。文中给出了 Harness 内部用户群的实例策略「静默复现并修复」，并强调「否则全程保持安静」。

**对我们的含义，也是我（助手）认为最有张力的一处**：投机执行在**个人版**是省下人的等待；在**企业版**它产生了三类**没人认领的运行事实**——后台尝试的过程、被丢弃的结果、以及「曾经尝试过但放弃了」这件事。按 §4 的规则，运行事实可丢弃；但按 §4.3.1，**「谁做过什么尝试」不能凭空消失**，否则失败会被重复尝试，且审计链断开。

**因此新增未决 Q-M**：投机执行产生的「被丢弃但确实发生过」的工作，在运行事实里如何留下**最小且可丢弃的痕迹**？


## 3.5 H1–H3 与三类系统的交接面 `[研究]`+`[助手]`

- **H1 × (c)**：来源一旦不止 GitHub，过程上下文不能只按「线程」组织。
- **H1 × (b)**：知识库按**来源**标注可信度，而非按渠道类型。
- **H2 × (c)**：异构 agent 不能共享内存过程状态，必须以**可序列化、可对账**形式存在。
- **H3 × (b)**：知识库是跨租户、跨进程共享资产，权限边界不能依赖「同进程同用户」。
- **H3 × BYOM/人工介入**：执行节点隔离后，「员工接管」通道成为必需项。
- **Watchdog × H2**：Watchdog 的异构最难——要判断「另一个 agent 有没有进展」，要求被观察方暴露**可判定的进展信号**，而非自述。
- **H1 × BOS**：Organization → Workspace 链可能就是 H1 的答案；也可能不是。
- **H3 × daemon**：进程隔离与 BYOM 的「手」是同一件事。没有可安装的 daemon，就没有可判定的故障域，也没有「员工接管」的落点。见 §2.1 与 Q-K。


## 3.6 用户明确指出、但此前从未进入备忘的四点 `[用户]`

以下四句都是你在本会话中直接说的，此前只被间接用到、没有被显式记录：

1. `[用户]` **「更通用 = 事件来源不只 GitHub/Feishu，不只单仓库单团队」**——这句既是 H1，也是**对企业级的正面定义**：企业级的第一性是**范围扩大**，不是并发数或模型强度。§1 只把它写成「对原型的冲击」，没把它写成「我们的目标」。
2. `[用户]` **「agent 异构：router / worker / watchdog 可以是不同实现、不同厂商，而不是绑定在 DSH」**——注意措辞是「**而不是绑定在 DSH**」，而不是「而不是绑定在某个 agent」。**DSH 被显式排除在必须项之外**，但它仍可以是三个承载项目各自的宿主实现。
3. `[用户]` **「多进程隔离也是需要的」**——这句话在原文里是**独立的一句**，与 BYOM、人工介入并列，不是 BYOM 的附属条件。§1 的 H3 已收录，但「它与 BYOM 是两条独立要求、只是共享执行节点」这一点此前没写。
4. `[用户]` **「员工机器上运行的 agent 可以加入到协作中」**——这是 BYOM 的**协作**含义，而不只是执行含义：员工机器上的 agent 是**参与者**（可以进 Router/Worker/Watchdog 任一角色），不是只被调用的算力。

**因此补一条设计前提（见 §7 第 20 条）**：企业级 Super-Agent 的第一个定义是**适用范围的扩大**（来源、参与者、部署位置），不是能力强度的提高。

## 4. 三类事实（本备忘的最高层结论）`[用户]`+`[助手]`

### 4.1 当时的表述顺序 `[用户]`

你在第一次提出这三者时，其秩序就是本次讨论的推理路径，后面所有结论都从这里长出来：

1. `[用户]`+`[助手]` **流程定义是「制度事实」**（谁在什么节点该做什么）——需要**版本化和审批** → 类 Flowable 的工作流系统/模块；
2. `[助手]` **业务知识是「认知事实」**（我们怎么理解这门生意）——需要**来源、置信、责任人，允许被推翻** → RAG 系统；
3. `[用户]`+`[助手]` **过程状态是「运行事实」**（这次任务进行到哪、谁在等谁）——**密度低、寿命短、可丢弃** → 记忆系统。

顺序有意义：先有制度（谁该做什么），再有认知（我们怎么理解），最后由运行事实承载两者在具体一次任务里的落地。**叙述顺序不要颠倒，否则「允许被推翻」这类性质会被误读到错误的层。**

### 4.2 四类判据 `[用户]`+`[助手]`

| | **制度事实**（a） | **认知事实**（b） | **运行事实**（c） |
| --- | --- | --- | --- |
| 定义（用户原话） | 流程定义：谁在什么节点该做什么 | 业务知识：我们怎么理解这门生意 | 过程状态：这次任务进行到哪、谁在等谁 |
| 谁有权写 | **人**（组织的权力） | 人 + agent 捕获，**人确认** | **系统** |
| 怎么算「对」 | 走完了、可审计 | 有来源、有置信、有责任人 | 与实际状态一致 |
| 怎么失效 | **被新版流程替换** | **被推翻**（保留旧版与推翻理由） | **直接丢弃** |
| 失效后果 | 高：已执行实例需重算 | 高：已基于它做过决定 | 低：可重建即可 |
| 因此需要 | 版本化 + 审批 + 实例迁移 | 溯源 + 置信 + 撤权 | TTL + 重建 |
| 用户给的性质 | — | **允许被推翻** | **密度低、寿命短、可丢弃** |

**防越界规则（待确认）**：运行事实「可丢弃」不是因为它不重要，而是因为**它不承担任何需要持久正确的判断**。一旦用过程上下文支撑授权或业务结论，它就升级为认知事实，不能再被丢弃。

**质量指标（待确认）**：运行事实的唯一质量指标是**可重建**——「丢掉以后能从事实流重算出同样的状态」。

### 4.3.1 五项职责不能都交给技术 `[研究]`

原报告把「采用时」的职责拆开，并明确这不是原型已实现的机制，而是组织必须自己保留的部分：

| 事项 | 组织决定 | 技术承担 |
| --- | --- | --- |
| 目标与优先级 | 选择工作、排序与资源投入 | 按规则筛选、排队、限流、展示积压；**Router 的调度顺序不构成业务优先级** |
| 请求与授权 | 谁能提出/修改/取消何种工作 | 校验主体与来源、记录 Mandate；**能发起任务 ≠ 能批准一切后续操作** |
| 意见与冲突 | 指定决策者、冲突处理方式 | 保留要求与来源；规则不足时交回负责人；**信息汇总 ≠ 裁决权** |
| 上下文与保密 | 哪些信息可对谁、在哪项工作中使用 | 按范围提供上下文并执行访问控制；**部署共享实例 ≠ 信息共享决策** |
| 交付与责任 | 完成标准、验收人、结果责任 | 提供可审阅成果与证据；**模型报告完成 ≠ 业务验收** |

**为什么这条必须保留**：它给「Super-Agent 能做什么」画了一条不可越过的线。我们的设计越贴近企业，越容易在无意间把「技术可以做的」当成「组织的决定已经做了」。这五条是**验收时的检查清单**，不是功能清单。

### 4.3.2 「授权」与「执行权限」是两层 `[研究]`

原报告的判断：**Mandate 回答「这个外部请求是否允许形成一项工作，以及在什么理由下继续」；DSH Permission Preset / 工具审批回答「Agent 能调用哪些能力，以及具体调用是否需要审批」。** 两者互补，任一方都不能代替另一方；尤其自动处理外部事件时，**事件发送者、仓库/组织规则、任务 Mandate、工具调用授权、操作系统权限**要分别审查。

**与本次讨论的衔接（待确认）**：这正是「调用身份」之外的另一条分层——调用身份回答「谁在调」，Mandate 回答「凭什么调」，工具授权回答「能调到什么」。三者需要分别建模，不能合成一个 `permission` 字段。

## 4.4 文章中被验证的四个设计因素 `[代码]`+`[研究]`

四项结论均来自《Super-agent 设计探索》原文（`[代码]` 指向原文归档）与原型研究材料 `[研究]`。它们不是「文章的实现」，而是文章提出且**实验或内部使用验证过**的设计因素。它们不会因为你选了 BOS/spring-ai-rag/BlueCortex 而消失——相反，它们正是三个承载项目**都不负责**的部分，因此属于 Super-Agent 自己的设计域。每项末尾的「对我们的含义」是 `[助手]` 级别的推断。

### 4.4.1 订阅与直通（Fast / Slow Path 的路由版）`[代码]`

文章第 3.2 节：**Router 只负责新任务的冷启动与跨任务协调；已确定归属的后续事件由程序直接发给对应 Worker，不经 Router 转发。** 依据是 Thread 上的订阅关系——「Router 根据 Thread 的初始事件创建 Worker 后，该 Worker 直接订阅该 Thread」。文中消融实验显示：去掉直通后完成时间基本不变，但 Router 决定数增加约 30%、读缓存 token 从 2323 万增至 3177 万（+37%）。**结论：直通不改善质量，但显著节省 Router 的开销。**

**对我们的含义（待确认）**：这是**路由成本**问题，与三个承载项目无关。BOS 的 MCP 调用是「谁调谁付」，若每个后续事件都经 Router，Router 会成为企业级规模下的单点费用与延迟源。原型实现了同一机制（Thread 订阅 + Intake 扇出），可直接借鉴其领域模型。

### 4.4.2 事件过滤的 Fast / Slow Path `[代码]`

文章第 3.1 节：环境事件流是「高噪音、低触发率」；把明确且稳定的高频判断固化为**确定性代码**（Fast Path），只把需要语义理解的事件交给模型（Slow Path）。原型的对应实现是 Policy gate（纯函数、不调模型）。

**对我们的含义**：企业级来源更多（H1），噪音比更高。**没有确定性前置过滤的 Super-Agent 会在第一步就被成本与延迟击穿。** 这条与「调用身份」「Mandate」共同构成准入链，但它是**性能前提**，不是授权前提。

### 4.4.3 异步 ReAct Loop（全双工）`[代码]`

文章第 4.1 节：把耗时的工具调用改为 `start()` / `stop()`，模型不等工具完成就能响应新消息；并注明「这一异步任务机制**已经在 DeepSeek Harness 中实现，但尚未默认开启**」。

**对我们的含义**：这是三类事实之外的一条**交互前提**——如果执行节点的调用是同步阻塞的，那么「人可随时介入」（BYOM 的意义所在）在技术上不可能。原型的对应做法是「前台命令 5 秒转后台作业」，它是这个机制的一种粗糙近似。

### 4.4.4 投机执行与「静默复现并修复」`[代码]`

文章第 3.4 节：在结果未必被采用时，Agent 先于后台尝试；有价值则交付，无价值则丢弃。文中给出了 Harness 内部用户群的实例策略「静默复现并修复」，并强调「否则全程保持安静」。

**对我们的含义，也是我（助手）认为最有张力的一处**：投机执行在**个人版**是省下人的等待；在**企业版**它产生了三类**没人认领的运行事实**——后台尝试的过程、被丢弃的结果、以及「曾经尝试过但放弃了」这件事。按 §4 的规则，运行事实可丢弃；但按 §4.3.1，**「谁做过什么尝试」不能凭空消失**，否则失败会被重复尝试，且审计链断开。

**因此新增未决 Q-M**：投机执行产生的「被丢弃但确实发生过」的工作，在运行事实里如何留下**最小且可丢弃的痕迹**？


## 5. 三个承载项目的事实基线 `[代码]`

### 5.1 制度事实 → BOS：已解，我们只消费 `[代码]`+`[助手]`

**用户的纠正**：「这些都是典型的工作流系统的问题，和 ai agent 的引入几乎没有什么关系！要是我们还打算『自己求解』，那就是『重新发明轮子』了。」

已核实（代码/文档证据）：

- **Flowable 在防腐层后**：`backend/src/main/java/com/wubuku/bos/adapter/flowable/`（`FlowableWorkflowAdapter` / `FakeWorkflowAdapter` / `DefaultWorkflowAdapterRegistry`）；provider key 一律不透明 `external*Ref` + `providerProfile`。
- **Agent-Friendly API 有定义**：六条性质——可发现、可解析、可恢复、可控、可审计、可演进；「不是一个单一标准」。
- **形态是 MCP 工具 + 严格行动边界**：draft / validate / compile / release approval / publish / claim / context read / result submission / reconciliation / human review 是**分离动作**；「Never infer approval from a chat message or a host confirmation dialog」。
- **人审通道独立**：`HUMAN` review 只能经认证的 BOS human work channel 创建；MCP token、execution grant、聊天记录、主机弹窗都不能创建它。
- **版本化 + 审批已解**：`Organization → Workspace → BusinessApplication → BusinessApplicationVersion → ApplicationBinding → WorkflowBinding → WorkflowComponentBinding`，每层带 generation；upgrade 与 rollback 都递增 installation generation。
- **三态语义是一等公民**：`UNKNOWN` / `RECONCILING` / `reconcile operation` / 幂等键 / `ACTIVATED` receipt。
- **双层 OS**：Agent Runtime OS（能不能工作）vs Business OS（该不该工作、为谁工作、谁负责）；六层中「② AGENT LAYER 保持可插拔」，本项目应掌握 ③④⑤。

**推论（待确认）**：(a) 不应出现在我们的模块清单里，应写成「由 BOS 以 Agent-Friendly API（MCP）提供，Super-Agent 只作为调用方和参与者」；「反对巨石」由此变成禁止项——**不复刻任何 BOS 已有的治理语义**。

### 5.2 认知事实 → spring-ai-rag：承载，但三处缺口 `[代码]`+`[助手]`

- **形态**：基于 Spring AI 的通用 RAG 服务；自研 JDBC 检索管线（pgvector HNSW + pg_jieba/pg_trgm + RRF K=60 + 查询改写 + 重排）。
- **来源** ✅：chunk 字符偏移 + `local_index_generation` + `content_hash`；证据快照只接受 `VECTOR`/`KEYWORD`，「回答只回到原始 Chunk」是硬约束。
- **置信** ✅：确定性断言；`expectedOutcome` 含 `INSUFFICIENT_EVIDENCE`（「证据不足」是一等业务结果）；「词法门槛失败不能直接宣布事实错误」；Judge 不能覆盖确定性失败。
- **允许被推翻** ✅：代际四元组（证据存稳定定位键，不存会重建的行 ID）；代际不存在判 stale；「不得覆盖原失败制品」；「诊断的新回答不能冒充历史答案」。
- **责任人** ⚠️ 缺口：`owner_principal_id` 只答「谁写的」，不答「谁负责、权威来自哪、谁有权推翻」。

**三处缺口**：① 责任人模型；② 写入路径（现有写入是文档入库，缺「agent 提请 → 人确认 → 落库」生产线）；③ 表达形式（检索系统 vs 结构化知识，KG 仍在评审、**未实施**）。

**规划状态（诚实标注）**：多租户「当前不支持」，方向已定（单仓单 schema、表永远租户化、单租户=N=1、四阶段），**未实施**；KG「前期技术讨论，未实施」，否决 Apache AGE 首发，第一版邻接表 + 递归 CTE。KG 评审的 P0 判断：**ACL 必须落在「证据→文档」层而非实体层**（实体跨文档聚合，可见性在证据上）。

### 5.3 运行事实 → BlueCortex（CE + EE）`[代码]`+`[助手]`

**CE 形态**：为 AI 助手提供跨会话持久化记忆。**瘦代理（Node.js，hook <200ms 返回）+ 胖服务器（Spring Boot 3.3，port 37777）+ PostgreSQL 16 + pgvector**。客户端：Claude Code、Cursor、OpenClaw、各语言 SDK；MCP 服务器；WebUI（git 子模块）。

**五个生命周期钩子**：SessionStart → UserPromptSubmit → PostToolUse → Summary → SessionEnd。→ `/api/session/start`、`/api/ingest/{tool-use,user-prompt,session-end}`。

**数据模型（CE，Flyway V25）**：

| 表 | 角色 |
| --- | --- |
| `mem_sessions` | 一次会话（`content_session_id` 唯一、`project_path`、`user_id`、`status` active/completed/skipped、`platform_source`、上下文缓存） |
| `mem_observations` | **基本单位**：`type`、`title/content`、`facts`/`concepts` JSONB、`files_read/modified`、`source`（tool_result/user_statement/llm_inference/manual）、`extracted_data` JSONB、`quality_score`、`feedback_type`、`step_number`、`content_hash`、三档 embedding（768/1024/1536）、tsvector |
| `mem_summaries` | 会话摘要 |
| `mem_prompts` | 用户提示 |
| `mem_pending_messages` | **崩溃恢复队列**：`status` pending/processing/processed/failed/skipped、`retry_count`、`tool_input_hash` |
| `message_queue_mapping` | 入队与持久化的映射 |

**可恢复性（用户特别指出的文档）**——`docs/evo-memory-implementation-zh.md` + `ARCHITECTURE-zh-CN.md` §「崩溃恢复」：

- 三段式：**实时**（`@Async` 事件监听器，虚拟线程）→ **兜底**（`PendingMessageProcessor`，`@Scheduled` 每 5 分钟捞 `pending`）→ **恢复**（`StaleMessageRecoveryTask`，把卡在 `processing` 超过阈值的重置回 `pending`；默认阈值 10 分钟，扫描间隔 5 分钟，`@PostConstruct` 启动时先跑一次）。
- **`POST /api/session/start` 的定位是「初始化或恢复会话，生成上下文注入和 CLAUDE.md 更新」**——恢复的产品形态是「重开会话时把上下文重新注入」，不是「恢复进行中的回合」。
- **准入与去重的真实机制**：靠 `AgentService` 的应用层 `existsBySessionAndTool` 检查 + Conversation 行 `PESSIMISTIC_WRITE` 锁串行化；`@UniqueConstraint` 声明存在但**数据库里没有该约束**（`ddl-auto: none`，无迁移创建），所以「数据库拒绝重复」不是保证。
- **代际意识存在但很薄**：`content_hash` + 30 秒窗口只在同一 Conversation 内抑制重复；没有代际/generation 概念，没有 fencing token，没有「旧 owner 的写入要被拒绝」的机制。
- **结构化提取**：提示词驱动的 YAML 模板 + Schema；**追加式（Append-Only）**——LLM 只输出 `add`/`remove`/`keep_hint`，服务端与库中完整先前数据合并，避免截断导致的静默丢失。

**EE 形态**：CE 的 Spring Boot 移植 + 企业多租户。已核实：

- **双数据库路径**：应用池 `cortex_app`（`NOBYPASSRLS`，每连接绑定 GUC）+ 平台池（`BYPASSRLS`，仅用于枚举活跃租户与 `/api/platform/**`）；平台池启动校验 `verifyRole`（必须 `rolsuper`/`rolbypassrls`，否则 FORCE RLS 把它过滤成 0 行直接失败）。
- **RLS 四件套**：`ENABLE` + `FORCE` + `tenant_id DEFAULT current_setting('app.current_tenant_id', true)` + `USING`/`WITH CHECK` 同一表达式。**GUC 未设置 → `NULL` → 0 行**，即 fail-closed 而非报错或读全量。
- **V21–V25 迁移**：`tenant/team/team_member/tenant_api_key/audit_event/usage_meter` → 7 张 `mem_*` 补 `tenant_id` → 11 张表 RLS → license/quota。

**与运行事实三条失效规则的对齐**：

| 要求 | BlueCortex 状态 |
| --- | --- |
| 系统有权写 | ✅ 钩子自动写入 |
| 与实际状态一致 | ⚠️ 见「切口」一节——它记录的是**助手会话**的事实，不是**多 agent 协作**的事实 |
| 可直接丢弃、可重建 | ⚠️ **恢复 ≠ 可重建**：恢复的是「被中断的处理任务」，不是「被丢弃的运行状态」；且恢复靠「时间阈值猜卡住」，不是靠代际或 fencing |

**跨三个系统的公约数（助手观察，待确认）**：BOS（不可变 pin + generation + `ACTIVATED` receipt + reconciliation）与 spring-ai-rag（`local_index_generation` + 代际四元组 + claim/lease/fencing + fail-closed）各自独立采用了「**不可变版本 + 代际 + 幂等 + fencing + fail-closed**」。BlueCortex 有幂等与 fail-closed，**缺代际与 fencing**。

**BlueCortex 的「Session 主语」与其产品定位（助手归纳）**：它是「**跨会话记忆**」而不是「会话内执行」——五个钩子里有 `SessionStart` / `SessionEnd`，但真正被持久化并向 agent 注入的是 `observation` / `summary`，而不是「这一轮的进度」。这解释了为什么它的恢复语义是「重开会话重注上下文」（见 §5.3），也说明**它与 (c) 里的「运行事实」只是部分重叠**：它提供的是「过去的运行留下的痕迹」，而 (c) 需要的是「此刻正在进行的运行」。这个区分直接决定了 Q-G 与 Q-I 的答法。

### 5.4 用户的判断：集成不是问题（推翻助手的隐性悲观假设）`[用户]`+`[助手]`

**用户原话要点**：「现在已有的三个组件/系统/模块，都已经『能』——或者接近『能』——和 Agent 集成。」

| 系统 | 它从第一天起就是什么 |
| --- | --- |
| BOS | 目标就是「把工作流系统通过 MCP Server 提供 agent 友好 API」，并留有跑通的端到端验收 |
| BlueCortex | 本质是 Claude Code 外挂记忆插件的 Java 移植——**插件形态是起点，不是增量** |
| spring-ai-rag | 虽无 MCP 端点，但 BOS 已给出完整范式（六条性质 + 生产模型 + 工具指南），可同样暴露 |

**用户的问题**：「个人版 agent（Codex、Claude Code）已经能以相当松耦合的方式集成它们，那我们构建企业版 Super-Agent，有什么理由不能集成它们呢？」

**助手承认的错误**：前几轮用「切缝」「需要另一次调用形态」等措辞，隐含假设「为个人助手设计的集成方式，放大到企业必然要重设计」。这是**未经检验的跳跃**。

**助手修正后的分析（三个层次，待确认）**：

1. `[用户]`+`[助手]` **协议层：能接，且已被证明。** BOS 的 MCP 工具、BlueCortex 的 MCP 服务器 + 四种 SDK、spring-ai-rag 的 REST，都是标准接口。此层不再存疑。
2. `[助手]` **松耦合层：「能」，但需要一条引用纪律。** 个人版的松耦合依赖一个隐含前提——一个人、一个 agent、一个工作目录、一条主线；于是 `mem_sessions` 按 `project_path` + `user_id` 分区、「恢复」=「重开会话重注上下文」、去重靠一条 Conversation 行锁就够了。多 agent 时该前提消失：同一 Thread 上可能同时挂着异构的 Router / Worker / Watchdog，而「谁在等谁」不属于其中任何一个。**这不是接口问题，是对象归属问题。** 解法不是新增系统，而是：**Super-Agent 自己持有协作编排事实，三个系统各自持有自己领域内的事实，两者通过 ID 互相引用，不互写对方的表。**
3. `[用户]`+`[助手]` **企业层：只多三件事，且都不要求改三个系统的集成方式。**
   - **身份与租户**（谁在调用）：BOS 有 Organization/Workspace，BlueCortex EE 有 RLS，spring-ai-rag 有多租户路线——**三者都已或正在从内部解决**，Super-Agent 只传上下文。
   - **策略与审批归属**（谁批准）：已在 BOS（Mandate / HUMAN channel），Super-Agent 只做调用方。
   - **异构 agent 的信任分级**（谁能调什么）：**唯一真正新增的**，且只发生在 Super-Agent 内部，不动外部系统。

**由此得出的关键区分**：工作量不是「三个系统 × 企业化改造」，而是「**一个薄编排层 + 三条引用纪律**」：

1. Super-Agent 只读写自己领域的运行事实；对方的 (a)(b)(c) 一律通过 ID 引用。
2. 企业级差异由被调用方负责，Super-Agent 只传上下文，不复制策略。
3. 跨系统一致性不做两阶段提交，只做「事件 + 可对账」——这正是三个系统各自的既有模式（BOS reconciliation、spring-ai-rag claim/lease、BlueCortex pending 队列）。

**对 Q-I 的影响**：原本担心的「缺代际与 fencing」被缩小——不是「给 BlueCortex 补一套架构」，而是「它的 pending 队列已提供重试语义，Super-Agent 只需在**自己的**编排事实上带代际」。

**助手由此提出的第一个候补新概念（待确认）——「调用身份」**：企业级新增的三项中，前两项（身份与租户、策略与审批）可由被调用方自行解决，引用规则一立就通；唯独**异构 agent 的信任分级做不到**——BOS 不知道、也不应该知道调用它的是 Router 还是某个 Worker。若这一点成立，Super-Agent 需要能自己做三件事：

1. 给每个角色发一个**可区分的调用身份**（Router 的身份 ≠ Worker 的身份）；
2. 调用 BOS / BlueCortex 时**携带该身份**，让对方能做二次判定；
3. 在**自己的编排事实**里记录「哪个身份、以什么依据、调了什么」——这是唯一能回答「这个 Worker 凭什么能改这条知识」的地方。

三条都在 Super-Agent 内部，不改外部系统。若成立，它实际上就是 Super-Agent 的**第一个真正的新概念，排在 (c) 之前**。


### 5.5 模块划分理由（原则，不是方案）`[用户]`+`[助手]`

1. 反对一体化巨石 / 单体；
2. 保护概念完整性——「领域」小一些，维护概念完整性的成本更低；
3. 复用已有开源积累或自己做过的 RAG、记忆系统——职责单一才容易找到「已经发明的轮子」；
4. 在架构阶段就做模块划分。

**另外两条从你最初表述中保留、但尚未在架构层展开的：**

- **「业务知识可以归入记忆模块，但这部分记忆偏原始、偏短期、与运行过程紧绑、信息与价值密度低」**——用户对 (b)/(c) 的分工与对「记忆」一词的**分层使用**（认知类记忆 vs 运行类记忆）。
- **「在架构阶段就做模块划分，别重新发明轮子」**——与「保护概念完整性」「复用已有轮子」并列为划分理由（即本条）。

**执行含义**：既然 (a)(b)(c) 已有承载者，「复用」意味着**不建，只接**。真正需要设计的是**三者之间的切缝**与三个角色的接缝。

**关于 (c) 的归入方式（用户已同意归入记忆，助手补充限定，待确认）**：可以归入记忆模块，但它是记忆模块里**唯一「不需要被相信」的那类记忆**——其他记忆说「这件事曾经如此」，过程状态说「这件事此刻如此」。其价值不是被记住，而是被核对。若归入记忆模块，建议在模块内部显式分成两类、两套验收：

- **认知类记忆**（(b)）→ 要求**可溯源**；
- **运行类记忆**（(c)）→ 要求**可重建**。

**风险（助手提出，对应 Q8）**：若「记忆」一词把 (b) 与 (c) 合成一个标签，会把两种验收标准混回一起——这正是「巨石」的实质代价（不是代码耦合，而是验收标准被合并）。

### 6.2.0 术语定义：thread 与编排事实 `[用户]`+`[助手]`

**用户的指认**：「按照你的解释，那不就是 thread『串联』下来的『一堆东西』吗？…… 『编排账本』这个词不是不能用，只是需要明确地定义后再用。」

**助手承认的错误**：从 Q-Z 到 Q-BA，助手用「编排账本」讨论了十几条规则（单写者、独立库、租户化、冻结、对账、保留期），却从未定义它，也没说明原型里是否有对应物。

**原型里的对应物**（已核实）：

| 原型对象 | 定义 | 证据 |
| --- | --- | --- |
| `Thread` | 外部来源上的一条事件流，key 为 `${source}:${id}` | `src/core/model.ts:157-180`、`:12` |
| `Thread.subscriptions` / `context` | 订阅该 Thread 的 Ticket；只读跟随的 Ticket | `src/core/model.ts:163-169` |
| `Ticket` | **Eval 接受后**才产生的工单，订阅来源 Trigger 上的全部 Thread，可再 follow 新 Thread | `src/core/tickets.ts:37-59` |
| `Assignment` | 一次执行尝试，属于 Ticket | `src/core/model.ts:211-232` |
| `TriggerDisposition` | 每条 Trigger 的去向（过滤/扇出/评估/判定），不授予任何权限 | `src/core/model.ts:41-47` |
| `Effect` / `Outbox receipt` | 持久副作用队列与对外消息回执 | `docs/drafts/prototype-architecture-as-built.md` §6 |

**Ticket 与 Thread 的关系**：多对多且不对称。Thread 是**独立实体、先于 Ticket 存在**，不属于任何 Ticket；Ticket 只订阅 Thread（`subscriptions`），并可选地 follow 它（`follows[]`，`own` 表示自己打开的）。一个 Thread 可被多个 Ticket 订阅；一个 Ticket 可订阅多个 Thread。

**本文的定义（建议采用）**：

> **编排事实** = 以某个 thread 为锚点、记录「它被怎样处理过」的一组事实，包括：该 thread 归属于哪个租户、被派发过几次给哪个角色、当前哪些任务在途、哪些外部副作用尚未对账。**编排事实不是一个新的领域对象，它是这四类事实的统称。**

| 术语 | 定义 | 存储 |
| --- | --- | --- |
| **thread** | 我们定义的协作线索，id 由 Super-Agent 生成（Q-AH / Q-BB） | 编排存储 |
| **编排事实** | 上述四类事实的统称，全部以 thread id 为锚点 | 编排存储 |
| **编排存储** | 承载编排事实的那一份数据库（Q-AB）；单写者（Q-Z / Q-AA）、按租户划分（Q-AC） | 独立库 |

因此，Q-Y / Q-Z / Q-AA / Q-AB / Q-AC / Q-AD / Q-AN / Q-AX / Q-BA 这些决定，**约束的对象是「编排存储」**，而不是某个名为「账本」的实体；「编排账本」若继续使用，只能作为「编排存储」的同义词，且必须在此处先定义。

| **Q-AD** | 编排存储的租户与 BOS 的 Organization / Workspace 的关系 | **只存不透明 `tenant_id` 与引用键**：组织、工作空间、成员全归 BOS，编排存储不定义第二套组织模型 | 与 §5.4「不复制策略、只说引用」一致；否则两套租户语义会漂移，或 RLS 无法本地执行 |
| **Q-AE**（已修正） | 编排存储的租户身份从哪里来 | **依赖抽象 port `TenantDirectory`**：能回答「这个租户 id 是否存在、是否有效」；编排存储只依赖此 port，**不依赖任何具体系统** | BOS 只是该 port 的**第一个 adapter**，置于防腐层；新增身份源（企业 IdP / SCIM 目录等）只需新增 adapter。**这是 port 定义问题，adapter 的具体归属是后话** |
| **Q-AF** | 与三个承载项目之间的 port 如何切分 | **按语义切分**：`FlowCatalog`（制度）、`KnowledgeQuery`（认知）、`CollaborationMemory`（运行）、`TenantDirectory`（身份）；不按系统切分 | port 描述「我们需要什么能力」，不描述「对方长什么样」；按系统切分会让 BOS 的对象链泄进我们的接口 |
| **Q-AK** | `TenantDirectory.resolve` 的返回形态 | **只返回不透明有效性凭证**：`valid(本系统身份)` / `unknown` / `invalid`；不返回名称、层级、成员 | 接口上出现名称或层级，就等于重新造一个「统一租户模型」；显示名属于各系统自己的投影 |
| **Q-AL** | 跨系统是否需要「租户映射表」 | **不需要**：每个系统各自定义租户抽象；跨系统只传不透明 id，由对方的 `TenantDirectory` 判有效 | 一旦建映射表，就是两个系统在协商共享同一概念，退回到统一租户模型 |
| **Q-AM** | `TenantDirectory` 返回的凭证是否带过期 | **带过期、需重验**：凭证含签发者与过期时间，过期后重新 resolve，不缓存永久结果 | Q-AL 已定不共享租户模型，因此没有集中撤销入口；只能靠凭证过期把「租户被停用」传播出去 |
| **Q-AN** | 租户被停用后，其编排事实如何处置 | **只读冻结 + 保留期**：立即禁写、禁派发，按合规保留期后删除，不立即抹除 | 立即删除会与节点上已产生的外部副作用（Q-X 的对账差集）脱节；冻结既停新写，又保留对账与审计所需历史 |
| **Q-AO** | 租户冻结时在途节点任务如何处理 | **不中断**：停止新派发，在途任务跑完并上报 | 外部副作用一旦产生就收不回，中断只会把 Q-X 的对账差集做大；停止新派发已阻断范围扩大 |
| **Q-AP** | 冻结期间如何判定在途任务已跑完 | **以节点上报为准 + 超时转待恢复**：上报完成才移出在途集合；长时间不报按 Q-V 转「中断待恢复」 | 执行方的沉默不能被当作「已完成」；冻结结束 = 在途集合为空，或每个剩余任务都有明确终态 |
| **Q-AQ** | 完成上报是否必须带副作用清单 | **必须带**：列出「已确认提交」与「可能提交、状态未知」两类；缺清单的上报视为不完整，不计为完成 | 对账差集（Q-X）唯一的信息来源就是完成时的这份移交；事后无法重建 |
| **Q-AR** | 节点声称「已确认提交」时凭什么认定 | **只认可核实的凭据**：必须带中心可独立核实的回执或外部引用；缺失则一律记「状态未知」，不论节点如何声称 | Q-X「编排事实不能由执行方自述」在完成上报上的落地；不做每次完成的远端重查 |
| **Q-AS** | 可核实凭据由谁去核实 | **来源 adapter 核实**：adapter 查证回执或外部引用，编排存储只收 `confirmed` / `unknown` 结论 | 与 Q-AF 的 port 切分一致；编排存储若直连外部系统，就同时承担了存储与来源适配两件事 |
| **Q-AT** | adapter 返回的 `unknown` 如何收敛 | **等待窗口 + 转人工**：窗口内重试核实；到期仍未知则升级为人工待处理，明确标注「无法自动核定」 | 不自动升级为 confirmed，也不静默抹除；复用 Q-Q 的人工出口 |
| **Q-AU** | 人工对 `unknown` 的裁定如何写回 | **追加三态署名记录**（`human_confirmed` / `human_not_occurred` / `human_undetermined`），保留决定人与依据，不改写原 `unknown` | 与 spring-ai-rag「不得覆盖原失败制品」同构；编排事实要能回答「谁在什么依据下判断的」 |
| **Q-AV** | 人工裁定的后果 | **只改变对账集合状态**：`human_not_occurred` 解除阻塞，`human_confirmed` 进入既有流程；裁定本身不直接触发外部动作 | 裁定是事实认定，不是业务决定；后续动作走编排与 BOS 流程，不让人工裁定成为旁路 |
| **Q-AW** | 待对账集合是编排事实的一部分还是独立系统 | **编排存储内的一类记录**，带自己的状态机与逐条留痕，不另建存储 | 另建存储就要再解决一次「与编排存储之间的一致性」 |
| **Q-AX** | 租户冻结期间对账类写入是否允许 | **禁业务、放对账**：派发 / 新 thread / 新任务全禁；核实结论、人工裁定、超时升级允许写 | 冻结要停的是「产生新工作」，清点旧工作恰是冻结后最该做的事 |
| **Q-AY** | 如何防止对账写入被当成绕过冻结的业务通道 | **固定状态迁移、无业务字段**：只能 `unknown → confirmed / not_occurred / escalated`，且只写结论、依据、署名 | 放开对账写入，就必须同时限制它的表达能力；约束应由类型决定，而非调用方自律 |
| **Q-AZ** | 冻结期间人工能否处置「转人工」条目 | **结论可写、业务动作延后**：人工可下结论并署名入账，但派生业务动作排队到解冻后或交 BOS 流程 | Q-AV「裁定只改集合状态」在冻结期最该生效；否则冻结对人工操作失效 |
| **Q-BA** | 对账历史与人工裁定的保留期 | **随租户保留期**：不单独设期限，与业务事实一同按 Q-AN 处理 | 对账记录的意义是解释业务事实；事实已清而记录孤存，既无解释力又是合规负担 |
| **Q-BB** | 企业级后 Thread 仍由外部来源定义还是由 Super-Agent 定义 | **Super-Agent 定义**：不透明 thread id，来源只提供可映射的来源引用（原型用 `source:id`，见 `src/core/model.ts:12`） | Q-AH 已定 thread id 由我们生成；若 Thread 仍由来源定义则该决定落不了地，`source:id` 也会把 Thread 钉死在单一来源上，与 H1 冲突 |
| **Q-BC** | 「哪些事件属于同一个 thread」由谁判定 | **来源 adapter 判定**：adapter 把来源引用映射到 thread，首次出现时申请新建；我们只签发与保管 thread 身份 | 合并规则是来源知识（PR 号 / 话题 id / 邮件串）；由中心统一判定会迫使我们维护所有来源语义 |
| **Q-BD** | 不同来源的事件能否落到同一个 thread | **只能由人显式合并**：adapter 不得自行跨来源合并；合并记录发起人、依据与承接租户 | 跨来源合并跨越两个 adapter 的知识边界，任一方都不具备完整依据；显式合并既保住 H1 的跨来源能力，也不让 adapter 互相越权 |
| **Q-BE** | 跨来源合并后如何呈现 | **保留来源轨道**：thread 下挂多条可分辨的轨道，合并只表示「同一条线索」，不改变事件的来源归属 | 合并依据必须可回查；压成单流会丢掉来源归属与时序比较 |
| **Q-BF** | 来源轨道里保存什么 | **只存引用 + 复核用元数据**（来源、事件 id、时刻、作者、是否人类）；正文留在来源侧，按引用取回 | 正文副本会让编排存储变成第二个来源系统，使 Q-BA 的保留期必须与来源侧对齐 |
| **Q-C1**（原 Q-C） | 一个租户的编排范围按什么划定 | **按「是否共享同一份编排事实」**：需要互见编排事实的参与者同属一租户；组织架构不作充分理由 | 范围决定谁看得见「谁在等谁」；按组织分会把不相干的工作绑进同一存储，按来源分则直接放弃 H1 |
| **Q-AG** | `CollaborationMemory` 如何对外表达「会话」 | **只暴露「协作线程」（thread）的现状与推移**；会话 → thread 的映射留在 adapter 内 | 上层不感知四个「会话」的主语差异，Q-G 因此不必先答；符合 Q-AF 的按语义切分 |
| **Q-AH** | 协作 thread 的 id 由谁生成 | **Super-Agent 生成不透明 thread id**；与承载对象的映射存进编排事实，承载项目只把它当外部引用键 | 标识规则归我们，不随承载实现漂移；一个 thread 可跨多个来源（H1），故不沿用来源 id；与承载对象的映射存进编排事实 |
| **Q-AI** | 同一 thread 的事件来自多个来源时，thread 归谁所有 | **归属唯一租户，创建时写定 owner**；其他租户只能引用并另建自己的 thread，再由 adapter 关联 | 归属不随事件来源漂移；跨租户共享写入权会直接破坏隔离 |
| **Q-AJ** | 跨租户的「引用」给出什么 | **指针 + 属主授权**：只给指针，对方向属主请求读取，由属主判定权限后返回；内容不离开属主租户 | 若引用附带内容副本，Q-AI 的归属就形同虚设，撤销权也随副本流失 |

## 8. 术语收敛（防止在后续架构文档里各说各话）`[助手]`

> 先读 §8.4：「实例」是本文多处决定的前提词，其定义决定了 Q-AI / Q-AJ 的实际含义。原文中的「实例」一词在 Q-AI 之前**没有定义**，是本次讨论中发现的缺口。

本次会话里同一个词出现过多种含义。下面把**已确定的**与**仍需你确认的**分开列出。

### 8.1 已确定，直接用

| 术语 | 含义 | 不能混用为 |
| --- | --- | --- |
| **制度事实** | 流程定义（谁在什么节点该做什么），版本化 + 审批 | 「配置」「规则」——会弱化其审批属性 |
| **认知事实** | 业务知识，有来源/置信/责任人，允许被推翻 | 「文档」「知识条目」——会漏掉置信与责任 |
| **运行事实** | 过程状态（进行到哪、谁在等谁），系统写、可丢弃 | 「日志」「指标」——它们不参与协作编排 |
| **Mandate** | 「这个外部请求是否允许形成一项工作」 | 工具权限、执行身份 |
| **可重建** | 丢掉后能从事实流重算出同样状态 | 「可恢复」——后者只表示「没做完的接着做」 |
| **调用身份**（候补） | 哪个角色在调用（Router ≠ Worker） | 用户身份、租户身份 |
| **编排事实** | 以 thread 为锚点的四类事实：归属、派发、在途、待对账 | 「过程状态」「运行状态」——它们暗示还有一份可丢弃的状态对象 |
| **编排存储** | 承载编排事实的那份独立数据库 | 「编排账本」——若使用，只能作为本词的同义词，且须先定义（§6.2.0） |
| **治理账本** | 组织侧的授权、审批、验收与审计记录（BYOM 三件套的第三件） | 「编排存储」——前者是组织的，后者是 agent 协作的；不加限定地单说「账本」会造成混淆 |

### 8.2 需要你确认的命名决定

**(c) 的名字建议从「过程状态 / 运行事实」改为「协作事实」**，理由有三条：

1. `[用户]`+`[助手]` **「过程」与 BOS 的 Process 冲突**——BOS 的 Process/Case 是制度事实，(c) 若也叫「过程」，会在跨系统讨论时被误认为同一对象。
2. `[助手]` **「运行」与 BOS 的 Run 冲突**——BOS 的 `WorkGraph` / `Run` 是业务实例，(c) 是 agent 协作实例。
3. `[用户]`+`[助手]` **它的真实内容就是协作**：谁在等谁、哪个回合属于哪个 Assignment、哪个角色授权了谁。「事实」表明它由系统记录、不需要被相信；(c) 的性质因此完整保留。

若采纳，本备忘后续以「**协作事实**」指代 (c)，并在首次出现时标注「即此前的过程状态 / 运行事实」。

### 8.3 仍然容易混的两组词

| 容易混 | 区别 |
| --- | --- |
| **会话（Session）** | BlueCortex 的 session = 助手会话；Super-Agent 的 Session = agent 实例；BOS 的 Run = 业务实例；spring-ai-rag 的 chat = 一次问答。四个都要显式限定主语（见 Q-G） |
| **状态（State）** | 「记录的状态」（事实）vs「推算出的状态」（投影）。Q-J 要求把两者分开 |

### 8.4 「实例」这个说法应当废弃

**用户的裁决**：「『实例 = 租户粒度的协作域』我赞成啊，那为什么要发明『实例』这个『概念』？还用了这么一个宽泛到近乎没边的名词！为啥不直接说『租户』？」

**结论**：如果两者是同一粒度，就不该有两个名字。本备忘此前反复使用的「实例」，其实就是**租户**；它之所以被发明出来，是因为讨论早期还没把租户边界定下来（Q-C），于是用了一个中性的代用词，后来又在 Q-O / Q-AC 里把它的外延收窄到了租户。

**修正后的说法**：

| 原表述 | 应改为 |
| --- | --- |
| 实例 = 一个共享同一份协作事实的协作域 | **租户** = 一份编排存储 + 一个租户边界 + 一组参与者 |
| 执行节点属于人，不属于实例 | 执行节点属于人，不属于**租户** |
| thread 归属唯一实例 | thread 归属唯一**租户** |
| 跨实例引用 = 指针 + 属主授权 | 跨**租户**引用 = 指针 + 属主授权（本质是跨租户，必须经属主授权） |
| 中心多副本、同一实例单写者 | 中心多副本、同一**租户**的编排存储单写者 |

**由此产生的三条追问（需要在下一轮确认）**：

1. **租户概念各自的含义**：每个系统定义自己的租户抽象（Q-AK / Q-AL）；Super-Agent 的租户 = 一份编排存储的边界，BOS 的租户 = 数据隔离根。二者**不要求恒等**，只需 `TenantDirectory` 能判有效。
2. **当前 adapter 是否用「一组织一租户」**：这是实现选择（Q-AE 修正），不影响接口；若采用，`tenant_id` 就是 Organization 的引用。
3. **部署与租户分开**：多个租户可以共用同一套部署，但各有一份编排存储。**部署 ≠ 租户 ≠ 编排存储**，三者必须分开说。

> 备注：§8.4 之前版本的「实例定义」是 `[助手]` 的提案，已被本条取代。全文其余位置仍使用「实例」的措辞**尚未逐一替换**，替换前以本条为准。
