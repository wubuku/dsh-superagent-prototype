> **文档性质**：架构设计，**尚未实现**。本文描述的是一条设计路线，不是一份关于已存在系统的说明；文中任何段落都不表示相应代码已经存在或可运行。

## 0. 设计起点与术语

### 0.1 三个硬要求

本设计由三条硬要求驱动。它们不是功能清单，而是约束：

| 要求 | 内容 | 为什么是硬的 |
| --- | --- | --- |
| **更通用** | 事件来源不只 GitHub 与飞书，也不只单仓库单团队 | 来源一旦可扩展，任何把来源写进模型的假设都要被推翻 |
| **agent 异构** | Router、Worker、Watchdog 可以是不同实现、不同厂商的 agent，不绑定 DSH | 角色一旦互不相识，任何靠共享内存或共享对象的协作都不成立 |
| **关键角色进程隔离** | 角色可以跨进程，甚至不必是 DSH | 角色一旦分处不同进程，任何单进程单写者的假设都要被推翻 |

表里提到三个角色，分工如下：**Router** 派活与对外沟通，**Worker** 干具体活，**Watchdog** 盯着各个 Worker 有没有进展。它们是三种职责，不是三个产品；异构的意思是每一种职责都可以由不同厂商的 agent 承担。表里的 DSH 指被借鉴的公开 Super-Agent 原型 DeepSeek Harness（第 10 章逐项对照）；「不绑定 DSH」「甚至不必是 DSH」是说任何一个角色都不默认长在它身上。

异构带来的直接后果是：角色之间只能靠**消息与状态**通信，不能靠共享内存或共享对象。这条通道具体怎么建，本设计未定，见第 11 章。

另有两条与之配套：**BYOM**（员工机器上的 agent 加入协作，为它提供执行环境）与**人工可介入**。后者不是可选项——BYOM 若没有人工介入就失去意义；多进程隔离也随之成为必要。

BYOM 的「手」不规定放在哪一层：**执行节点可以是云端，也可以是员工自己的电脑**；而**云端节点里跑的 agent 仍可以把它的「手」放到某个员工控制的本地电脑上**——即 BYOM 可以嵌套：云端的脑 + 员工机器上的执行环境。本设计对这两种形态都成立，因为本设计钉的是「任务域绑定执行环境」，而不是规定「脑」在哪一侧。**这不是「二选一」，两种形态是预期内的并列选项**——本设计不支持「只支持一种模式」的读法。**怎么在员工的机器上构建那个「手」（本地 daemon 的形态、注册、连接与授权）仍是未决问题**——它属于第 11 章那一类「本设计没有收敛」的问题（第 11 章列了四项，这一项不在其中，因为前四项都假设执行节点已存在；本设计先把执行环境的位置与纪律定下来，daemon 的构建留到节点落地时再答）；本设计只要求它满足 4.5 节的任务域纪律与第 7 章的隔离要求。

三条硬要求都不是「做得更强」，而是「扩得更广」：事件来源更多、参与者更多、部署位置更多。因此本文先定边界与归属，再谈效率（结论 20）。

### 0.2 企业级盲区：业务流程与隐性知识沉淀

被借鉴的文章与原型只设计了一台「接活、派活、记账」的机器，没有设计这台机器怎么**懂业务**。它们只建模了「任务」，没有建模「组织」：回答「这件事派给谁、跑到哪」，不回答「这类事情本公司怎么做」与「上次那个例外是因为什么」。这正是企业级的盲区。

补的办法是先把三类事实分清，再各自归位。前两类交给既有系统，第三类没有现成的承载者，由本项目自己持有：

| 事实 | 承载什么 | 承载者 | 本文中的位置 |
| --- | --- | --- | --- |
| **制度事实** | 流程定义、版本与审批 | BOS（既有系统） | 1.1 节 |
| **认知事实** | 业务知识，含 agent 捕获梳理的隐性知识 | Spring-AI-RAG（既有系统） | 1.2 节 |
| **运行事实** | 这次进行到哪、谁在等谁——落到本项目就是**编排事实**（本文统一用这个词，不叫「过程状态」） | **本项目**（编排层自己） | 4.3 节 |

第 1 章还会出现第三个既有系统 BlueCortex。它不在这张表里：它承载的不是上面任何一类事实，而是**单个助手跨会话的记忆**——各参与者各自的「过去做过什么」。它与运行事实只有部分重叠（它保存的是过去的运行留下的痕迹，不是此刻正在进行的运行），它的位置在第 1.3 节单独交代。

认知事实的承载者不是「记忆系统」：记忆服务于单个 agent 的连续性，知识库服务于整个组织，需要版本、来源、责任人与撤回。运行事实可以归入记忆，但它是偏原始、偏短期、与运行过程紧绑的那一类，价值密度低；它的验收标准是可重建，不是可溯源。本文不单独使用「记忆」一词，提到时必须说清是认知类还是运行类（结论 82）；术语也先在文内收敛，否则跨系统讨论会把同名不同义的对象合成一个（结论 17）。

### 0.3 划分理由

- **反对一体化巨石**：把三种验收标准塞进一个模块，比代码耦合更难维护。
- **保护概念完整性**：领域范围小一点，维护概念完整性的成本就低一点。
- **复用已有的轮子**：职责单一才容易找到已经做过的东西；三个既有系统都不重做。
- **在架构阶段就做划分**：模块边界是架构决定，不是实现期的重构产物（结论 6）。

### 0.5 命名纪律（概念完整性）

**本表是唯一真源。** 任何文档、图表、代码、代码注释、与外部系统的对照材料，对表中概念的称呼必须与本表一致；发现不一致，改称呼，不改定义。借用外部概念时遵守五条：

1. **先查表，再命名。** 表里已有对应概念，就用表中的词；表里没有，才考虑新增，新增须进表并写明「含义」与「不要混用为」两栏。
2. **不沿用来源系统的名称。** 从别的系统（原型、BOS、A2A、UHP、Herdr、客户方案…）引入概念时**换名**，并在 §0.6 外来词映射表登记；换不了名的（如 Mandate）必须在表里写清「不要混用为」。
3. **一词一义，一义一词。** 不允许一个词在本项目里承载两种含义（如原型把「来源轨道」叫 `Thread`）；也不允许两个词指同一概念（同义异名必须删掉一个）。
4. **引用外部术语时写对照，不做替换。** 说「A2A 的 Task」时明确标注来源与差异，不得直接写成「Task」冒充本项目单元（A2A 报告已确立此纪律）。
5. **命名评审进 ADR。** 任何新概念或改名走 ADR 与修订窗口（与契约同一窗口），改后在夹具、图表、代码注释中同步；编译期/测试期能守的（如枚举名、schema 字段名）必须加守卫测试。

**为什么值得写进架构：** 同名不同义是最难查的一类缺陷——它不进 bug 列表，只让人「照着错的东西开发」。原型 `Thread` 一例已说明代价：一个词的偏差导致入口、创建、归并三处判断全错。

## 1. 我们已有的三个系统

本章先交代三个既有系统各自在什么位置、承担什么、不承担什么。后文与配套图表一律使用本章的标准化称呼：**BOS**（Business Operating System，业务操作系统）、**Spring-AI-RAG**、**BlueCortex**。

### 1.1 BOS —— 制度事实的承载者

BOS 是面向组织侧的业务操作系统。它管理流程定义、流程版本与审批、业务应用与其安装关系、工作空间以及运行中的业务实例。它已经以 MCP（Model Context Protocol）工具的形式，把这些能力暴露为面向 agent 的接口，并在接口层面区分了「起草」「校验」「编译」「审批」「发布」「领取」「提交结果」「对账」等动作——这些动作彼此分离，任何一步都不能被聊天消息或弹窗推断为已批准。

BOS 对本项目的意义是：**制度事实（谁在什么节点该做什么）不在这里实现，只在 BOS 里存在。** 本项目不建流程引擎、不建审批链、不建版本治理，也不复刻其中任何一项（结论 7）。

它也有限度：BOS 关心「一笔业务办到哪」，不关心「哪些 agent 在互相等什么」。后者不属于它的领域。

### 1.2 Spring-AI-RAG —— 认知事实的承载者

Spring-AI-RAG 是检索与知识服务。它把文档切分、嵌入、索引，并以混合检索与重排回答查询。它有三个特点值得单独提出：每一段被引用的内容都能回到原文的具体位置；检索结果带有分支诊断；证据不足被当作一种正常结果，而不是故障。

它对本项目的意义是：**认知事实（我们怎么理解这门生意）存放在这里，而不是存放在任何 agent 的上下文里。**

它也有限度：既有归属字段只答「谁写的」，不答「谁对知识负责、谁有权推翻」；写入路径是文档入库，没有「agent 提请、人确认、再入库」这样的生产线；它存的是可检索片段，结构化程度取决于知识形态（图谱能力与多租户支持都仍在迭代、未实施；结论 8）。因此「知识的责任人」与「知识写入流程」不能当作 Spring-AI-RAG 已具备的能力；这两件事要由本项目的知识生产线补上（见第 9 章）。

### 1.3 BlueCortex —— 参与者的跨会话记忆

BlueCortex 有社区版与企业版两个版本。社区版为单个 AI 助手提供跨会话持久化：由轻量的钩子代理把事件转发给后端，后端抽取观察、生成摘要、检索历史，并在新会话开始时把上下文重新注入。企业版在同样的功能之上实现了多租户：租户以数据库行级隔离，连接未绑定租户时读到零行而不是报错，平台侧与管理侧的连接被分开。

先说清它是什么、不是什么。它是 Claude-Mem 的 Java 移植；Claude-Mem 是一个**外挂式**记忆插件——最初面向 Claude Code，后来扩展到 Cursor、Codex 等更多 agent。「外挂」的含义要读准：agent 自己的会话状态（这一轮的上下文、工具输出、工作记忆）始终留在 agent 的运行时里，随会话结束而消失，**不因接入 BlueCortex 而改变**；BlueCortex 只从旁边观察——钩子在会话开始、用户提交、工具调用、会话结束时触发，后端异步地把事件提炼成观察与摘要，等**下一次**会话开始时再注入回来。它持久化并向 agent 回供的是 `observation` 与 `summary` 这类派生痕迹，从来不是「这一轮进行到哪」。

它对本项目的意义由此而来：**它是参与者一侧的跨会话记忆，不是协作一侧的状态。** 每个 agent——尤其是执行节点上的 Worker——靠它记得上次同类工作怎么做的、试过什么、为什么放弃；这条「个人侧的连续性」与第 9 章组织侧的知识生产线互补。而多个 agent 围绕同一条线索协作时，「谁在等谁」不属于其中任何一个 agent 的记忆：它既不在 agent 自己的会话里，也不在 BlueCortex 从会话里提炼出的摘要里。协作状态的承载者只能是编排事实（结论 9）。

这也决定了它的两个限度（结论 86）。其一，它保存的是派生痕迹，不是权威事实：对账、授权、验收都不能引用「BlueCortex 这么记得」作依据。其二，它的记录单位是助手会话（按项目路径与用户划分），多条线索的痕迹在同一份记忆里交错——从它那里取「某条线索发生过什么」可以，取「这条线索现在处于什么状态」不行。

### 1.4 三者与「缺口」的关系

三个系统各自在自己的领域内已经解决或正在解决身份、隔离、版本、幂等这些企业级问题。仍然没有归属的，是**执行节点**：负责把任务真正做出来的执行面——可以是员工机器上常驻的进程（借用员工环境那只「手」），也可以是云端的节点（其内部 agent 仍可把「手」伸到员工机器上，见 0.1 节）。它的故障域、文件与凭据边界、租户边界不由上述任何一个系统承担（结论 14）。这一点决定了第七章的内容。

## 2. 三类事实与失效规则

本章是全篇的推导起点。后面的装配、实体、接口、生命周期，都能从这一章的约束推出，而不是从任何既有实现继承来（结论 1）。

### 2.1 三类事实

| 事实 | 内容 | 谁有权写 | 怎么算「对」 | 怎么失效 |
| --- | --- | --- | --- | --- |
| **制度事实** | 流程定义：谁在什么节点该做什么 | 人（组织的权力） | 走完了、可审计 | 被新版流程替换 |
| **认知事实** | 业务知识：我们怎么理解这门生意 | 人 + agent 捕获，**人确认** | 有来源、有置信、有责任人 | 被推翻，且保留旧版与推翻理由 |
| **运行事实** | 过程状态：这次进行到哪、谁在等谁 | 系统 | 与实际状态一致 | 直接丢弃 |

### 2.2 三条失效规则

1. **制度事实失效时，代价最高**：变更流程会牵涉已经执行过的业务实例。因此制度事实必须版本化并由人审批，不做「就地修改」。
2. **认知事实失效时，代价次高**：曾经基于它做出过的决定，事后可能不成立。因此认知事实必须带来源、置信与责任人，允许被推翻，并且被推翻时保留旧版。
3. **运行事实失效时代价最低**：它的密度低、寿命短，可以直接丢弃，只要还能从事实流重算出同样的状态。因此它唯一的硬性质量指标是**可重建**，而不是「可恢复」——后者只回答「这条处理任务跑完没有」，前者回答「现在谁在做什么、谁在等谁」（结论 12）。

### 2.3 一条防越界规则

已定的是这一条：**运行事实不得承担授权或业务结论**（结论 2）。它在后文两处落地：6.3 节的人工裁定不直接触发外部动作，9.3 节的重判只挂接不自行扫描。

由此可以推出，但本文尚未当作已决：运行事实「可丢弃」的边界在于它不承担需要持久正确的判断；一旦有人用它去支撑一个授权或一个业务结论，它就应被视为认知事实，不能再被丢弃。这是一条推论，不是已决条目。

运行事实可以作为运维观察的输入——例如判断某个 agent 有没有进展——但那是观察，不是业务决定。两者不可混同。

## 3. 装配：本项目与三个系统的关系

### 3.1 本项目的位置

本项目是一个**编排层**：它负责把「事件来了该交给谁、谁在跑、跑完对没对上账」记录下来，并在这套事实上做调度与判断。它不负责制度、知识，也不负责助手的跨会话持久化——这三件事分别由 BOS、Spring-AI-RAG、BlueCortex 提供（结论 31）。

由此得出「反对巨石」在本文中的具体含义：**本项目不得复刻任何一个承载系统已有的治理语义**（结论 7）。流程版本、审批、修订记录、知识索引、助手会话都不在这里重新发明。

值得先说清一件事：**把这三个系统接起来并不难**。它们从第一天起就是面向 agent 集成的，个人版 agent 已经能以松耦合方式用上。企业级真正新增的差别不在「能否接入」，而在「编排契约归谁、企业级属性由谁负责」（结论 11）。

### 3.2 只有抽象，没有具体系统

本项目与三个承载系统之间，只通过抽象接口相连（结论 37）。本项目**不依赖** BOS、Spring-AI-RAG 或 BlueCortex 中的任何一个具体实现；每一个承载系统都只是某个接口的适配器。这意味着：

- 更换知识服务，不需要修改编排层；
- 增加第二个身份来源（企业的身份目录、单点登录、目录同步），只是增加一个适配器；
- 三个承载系统本身如何演进，不影响编排层的概念结构。

### 3.3 接口按语义切分

接口按「本项目需要什么能力」切分，而不是按「对方系统长什么样」切分（结论 38）：

| 接口 | 回答什么 | 典型适配对象 |
| --- | --- | --- |
| **FlowCatalog** | 有哪些制度、某个流程版本是否有效、能否启动一次业务实例 | BOS |
| **KnowledgeQuery** | 某条知识是否成立、依据是什么、责任角色是谁 | Spring-AI-RAG |
| **CollaborationMemory** | 这条线索上发生过什么——参与者留下的痕迹与推移 | BlueCortex |
| **TenantDirectory** | 这个不透明的租户标识是否有效 | BOS、或任何企业身份目录 |

接口里不出现任何一方系统的对象名、层级名或字段名。凡是需要「统一租户模型」的地方，都是切分错误的信号（结论 43）。

还有一条值得注意的公约数：**不可变版本 + 代际 + 幂等 + fencing + 失败关闭**是这类承载系统的公共做法（fencing 指让旧写者迟到的写入被拒绝的机制）——BOS 与 Spring-AI-RAG 各自独立地采用了整套，BlueCortex 只有幂等与失败关闭，缺代际与 fencing。这不是巧合，是这类系统的必要条件（结论 10）。本项目的编排存储也必须说同一套话。

### 3.4 每个系统各自定义自己的租户

四个系统对「租户」各有含义：BOS 里它是数据隔离根；Spring-AI-RAG 里它是检索隔离单位；BlueCortex 里它是数据库行归属；本项目里它是**一份编排存储的边界**。这不要求它们彼此恒等，也不建任何映射表（结论 43）。

接口之间传递的是**不透明的租户标识**；对方能否接受，由对方的 `TenantDirectory` 判断。两个系统不需要先就「租户」达成一致，只需要各自能回答「这个标识对我是否有效」。

本项目的租户边界就是**编排范围**：需要互见编排事实的参与者同属一个范围。组织架构不是充分理由——同一部门可能分出两条不相交的线索，不同部门也可能共享一条（结论 65）。范围与 BOS 的 Organization 不要求同一粒度，是否对齐属于适配器的实现选择（结论 66）。跨范围要协作时，不建跨范围的 thread，而是各自建 thread 并引用同一个 BOS 业务实例（结论 67）。

## 4. 核心实体

### 4.1 thread

**thread** 是一条协作线索：一组围绕同一件事、来自一个或多个来源的事件，加上围绕它们的编排事实。thread 的标识由本项目生成，不沿用任何来源系统的标识（结论 40、60）。

thread 有以下不变量：

- **归属唯一租户，创建时写定，不可更换**（结论 41、68）。需要把一条线索交给另一个租户时，新建 thread 并引用旧的，而不是转移归属。
- **跨租户只能引用，不能共同写入**（结论 41、42）。引用只给指针，由属主授权后返回可见内容，内容不离开属主租户。
- **结束是终止态**（结论 69）。当它的全部来源轨道都已关闭、且在途任务为零时结束；结束之后不再接收事件，后续同类事件新建 thread。

### 4.2 来源轨道

一条 thread 下挂若干**来源轨道**，每条轨道对应一个来源适配器送来的事件。轨道之间可以合并（例如 GitHub 上的讨论与即时消息里的话题是同一条线索）。**合并不是只能靠人**——按信号强度分三级（结论 62 的修正，见下方倾向）：

| 级 | 信号 | 处理 |
| --- | --- | --- |
| **引用合并** | 来源自己声明了关联：邮件主题带工单号、PR 链接 issue、消息引用同一对象 | **自动**——解析显式引用即锚到对应 thread，落带依据的合并记录。这是解析不是判断，零模型成本，覆盖企业实践的大多数 |
| **推断合并** | 无显式引用但证据强（同次触达、同一外部对象、同实体+时间窗） | Router 提议；高置信自动生效但打「推断合并」标记、进 Watchdog 复核清单；按精确率优先调闸门（漏合并可事后补、错合并不可逆） |
| **人工合并** | 无引用、置信不够 | 人发起，素材取台账（correlated 键等）——兜底，不是主路径 |

合并之后仍保留多条可分辨的轨道，不压成一条事件流（结论 63）。任何一条合并都必须有依据：要么解析出的显式引用，要么署名的推断依据 + 复核标记——**无据合并不存在**。另外，多数「多来源同一件事」的工作场景**不需要合并到这一层**：让一个 Ticket 订阅多条 thread 即可（订阅归并，见 6.4）；thread 级合并只服务于「事项身份超越单个工单」的需求（锚业务实例、长期线索、报表口径）。

轨道只保存**引用与复核用的元数据**（来源、事件标识、时刻、作者、是否为人类），不保存正文；正文留在来源侧（结论 64）。这样编排存储不会变成第二个来源系统。

来源适配器只做一件事：把来源侧的事件折算成 **track key**（`${source}:${id}`）并送来。**它不判断「哪些事件属于同一条 thread」**——那是编排层按下一段的确定性规则完成的；跨来源的归并规则属于来源知识，走 4.2 三级合并，不在适配器里。

把这里的「判定」说精确——它**不含任何智能判断**，只有两层确定性操作：**事件级幂等去重**（同一事件重复投递，按 `(来源, 事件标识)` 等值丢弃）与**轨道级 get-or-create**（对 track key 做字典等值查找：有则复用、无则新建）。因此 **thread 与轨道在创建时刻严格 1:1；合并之后是 N:1——多条轨道锚到一条 thread（本表比值一律读作「轨道 : thread」）**。thread 的身份不派生自 track key（结论 40/60 的工程含义：若派生，合并就得改 id，与归属写定不可换冲突，结论 41）。原型还为此存了归并素材：每次事件触达时记录「同一次触达的其他轨道键」（`correlated`）——这是**推断合并**的输入之一（见本页上方三级表），人发起合并时依据也已在台账里。

### 4.3 编排事实

**编排事实**是运行事实在本项目里的具体形态：以 thread 为锚点，由四类事实组成，不是一个新的领域对象。第 2 章说的「运行事实」是这一类事实的通称，落到本项目就是下面这四类：

| 事实 | 内容 |
| --- | --- |
| **归属** | 这条 thread 属于哪个租户，何时由谁创建 |
| **派发** | 在什么时刻把一个任务派给了哪个角色 |
| **在途** | 哪些任务当前在某个执行节点上尚未结束 |
| **待对账** | 哪些外部副作用还没有被确认 |

四类事实之外，编排事实还存指向外部对象的不透明引用键——例如该 thread 对应的业务实例、对应执行记录。本项目**不缓存**这些外部对象的摘要（结论 85）；摘要一旦存进来，就是第二份业务事实。

还有四件事不外包给任何承载系统，属于本项目自己的设计域（结论 18）。**订阅直通**：已归属的后续事件不经 Router 转发，省下决定数与 token。**确定性前置过滤**：否则企业级来源的噪音会把成本打穿。**异步执行调用**：非阻塞，否则「人工随时介入」不可能。**投机执行**：它会产生无主的运行事实；投机留下的「被丢弃但发生过」只记一条最小尝试记录——做了什么、结果、为何放弃，产物不留（结论 80）。

### 4.4 编排存储

**编排存储**是承载编排事实的那一份独立数据库（结论 34）。它与 BOS、Spring-AI-RAG、BlueCortex 的数据库彼此独立，跨系统只用标识引用。它按租户划分，从第一天起就带租户列，单租户场景等价于「只有一个租户」（结论 35）。它只保存不透明的租户标识，不复制任何组织层级（结论 36）。

需要与另一个「账」区分开：**治理账本**属于组织，记录谁批准、谁验收、谁负责，是业务系统侧的概念；**编排存储**属于 agent 协作，记录派给谁、跑到哪、对没对上账。两者不是同一个东西，本文不混用。

### 4.5 任务域与移交包

**任务域**是执行节点上为单个任务建的独立执行环境：独立工作目录、独立凭据注入、独立网络出口策略。节点本身不持有任何租户凭据；凭据随任务域创建、随任务域销毁（结论 22）。

任务域绑定的是**执行环境**，不是「脑在哪」：同一个任务域可以整个落在云节点上（脑与手都在云），也可以由云节点里的 agent 把「手」伸到员工电脑上的执行环境（云脑 + 本地手，即 BYOM 嵌套，见 0.1 节）。两种形态共用同一套任务域纪律。

换一个角度：**任务域是信封，agent 会话是住户。** 人看见、能接管、可销毁的单元是信封，不是裸会话——会话是执行层的东西，信封才是隔离与焚毁的边界。一任务一域是硬约束；一个域里跑几个会话（例如子代理）属于实现细节，但任何会话都不比信封活得久：域销毁，会话随之结束，只留移交包。

**移交包**是任务域销毁时留下的唯一残留：一份只读清单，包含改动摘要、日志摘要与归档引用，放在节点本地的隔离区，到期删除。它不包含凭据，也不包含租户原始数据的副本（结论 23）。移交包的存在是为了让人还能接手，而不是为了在节点上保留数据。

到期时限由租户一侧下发，删除由节点执行并回报——约束来自租户，动作发生在数据所在处（结论 24）。节点的本地空间硬上限**不授权删除**：触及上限时节点降级并回报，由 Router 改派；删除的唯一依据是合规时限（结论 25）。

## 5. 接口的语义契约

本章只写每个接口「问什么、答什么、不答什么」，不写实现，也不写传输方式。

### 5.1 FlowCatalog

**问**：某个流程版本是否仍然有效；能否以某个租户的身份启动一次业务实例；某次业务实例的当前状态。

**答**：有效性、可启动性、以及一个不透明的业务实例引用。

**不答**：本项目的 thread 是什么、哪些 agent 在跑。也不答「这次工作该不该做」——那是 BOS 的授权语义，本项目只读取其结果。

### 5.2 KnowledgeQuery

**问**：某条知识是否成立、依据为何；某条知识的责任角色是谁。

**答**：结论、依据引用、置信表述、责任角色。

**不答**：也不接受「写入」。知识只能通过提案进入，由人确认后才入库（结论 73）。调用方不能通过这个接口改变知识。

### 5.3 CollaborationMemory

**问**：这条线索上发生过什么——各参与者留下了什么痕迹、做过什么、当时依据什么。

**答**：按时间排列的痕迹与推移。它们来自参与者的记忆（1.3 节）：是过去的运行留下的记录，不是此刻的运行状态。

**不答**：「现状」。谁在等谁、哪些任务在途，是编排事实，本项目自己持有，不从任何参与者的记忆里问（结论 86）。本接口也**只暴露协作线索，不暴露「会话」**（结论 39）：四个系统里「会话」的主语各不相同——助手会话、agent 实例、业务实例、一次问答——线索到会话的映射留在适配器里，上层不必先解决这个问题。

### 5.4 TenantDirectory

**问**：这个不透明标识对你是有效的吗。

**答**：三种结果之一——有效（附上本系统内部的不透明身份）、未知、无效。**不答**名称、层级、成员名单（结论 43）。接口上出现这些内容，就等于重新造一个「统一租户模型」。

返回的凭证带过期时间，过期后需要重新询问（结论 45）。这是让「租户被停用」能够传播出去的唯一途径——因为没有集中撤销入口，也没有理由再建一个。

## 6. 生命周期

### 6.1 thread 的生命周期

1. **建立**：来源适配器送来一条事件（携带 track key）；编排层按 track key 做确定性 get-or-create——没有对应 thread 就新建，本项目签发标识并写定归属。适配器不判断归属，判断只发生在后续的合并（4.2 三级）。
2. **生长**：同一 thread 下的新事件进入各自的来源轨道；跨来源合并按信号分级（引用合并自动、推断合并带标记、人工兜底，见 4.2）。
3. **结束**：全部轨道关闭且在途任务清零，thread 进入终止态（结论 69、70）。适配器只报告「我这条轨道关闭了」，是否结束由编排层决定。

结束之后不可复活。这是刻意的：如果它可复活，同一个标识就会承载两段不同历史。

结束不等于账已清。thread 的结束条件里没有「待对账清零」，因此一条已终止的 thread 上可以挂着未决的对账条目。它们照旧按 6.3 节走完自己的状态迁移，只是不再有新事件进来——待对账条目是编排存储内自带状态机的记录（结论 55、57），结束一条 thread 只改它自己的状态，并不删除挂在其下的记录。

### 6.2 任务域的生命周期

1. **生成**：编排层把任务派给某个执行节点；节点为它建立一个任务域，并在任务域内注入该任务所需的能力凭据。
2. **执行**：agent 在任务域内调用能力，不接触凭据本身。
3. **上报**：任务完成时，节点必须提交一份副作用清单，区分「已确认提交」与「可能提交、状态未知」（结论 49）。没有清单的上报视为不完整，不计为完成。在途是否结束以节点上报为准；节点长时间沉默不算完成，而是转为「中断待恢复」（结论 48）。
4. **销毁**：任务域销毁，只留移交包（结论 23）。

### 6.3 待对账条目的生命周期

一条外部副作用在没被确认之前，是一个**待对账条目**；所有条目合起来叫**待对账集合**。它们都是编排存储内的一类记录（结论 55），状态迁移固定（结论 57）：

```
未知 ──核实成功──> 已确认
  │
  ├──核实确认未发生──> 未发生
  │
  └──等待窗口到期仍未确定──> 转人工 ──> 人工确认 / 人工认定未发生 / 人工无法判定（窗口到期后升级，结论 52）
```

三条规则约束这条链：

- **「已确认」只认可核实的凭据**（结论 50）。节点声称已提交，但没有可独立核实的回执或外部引用，一律记为「未知」。
- **核实由来源适配器承担**（结论 51）。编排存储只收结论，不直接访问外部系统；对账以编排层收到的回执为准，节点记录只用于标记「未知」（结论 30）。
- **人工的裁定是追加的署名记录，不改写原记录**（结论 53）。每条裁定都带决定人、依据与时间；原先的「未知」保持原样。

人工裁定只改变待对账集合的状态，**不直接触发任何外部动作**（结论 54；这是 2.3 节那条防越界规则的落地）。三种裁决对应三种状态：`人工确认` 使条目转为 `已确认`，`人工认定未发生` 转为 `未发生`，`人工无法判定` 维持 `未知`。转为 `未发生` 解除被它阻塞的工作，转为 `已确认` 让相关工作回到既有流程，维持 `未知` 则只留下署名记录——既不假确认，也不静默抹除。至于「接下来做什么」，那是业务决定，走编排层与 BOS 的流程，不让人工裁定成为旁路。

### 6.4 Ticket 与 Assignment 的生命周期

五个对象构成一条链：**来源轨道 → thread → Ticket → Assignment → 任务域**。前两级（6.1/6.2 节）管「事情与线索」，后三级管「这件活与它的执行」。谁创建什么：

| 对象 | 创建者 | 时机 |
| --- | --- | --- |
| 来源轨道 | 来源适配器 | 事件到达，确定性登记（6.1 建立步骤） |
| thread | 编排层 | 首个事件触达且无对应线索；id 由本项目签发，归属写定 |
| **Ticket** | **编排层的接受决策** | Eval 接受那一刻；同一决策同刻带上 Mandate、订阅与首个 Assignment（原型 `Tickets.create` 语义沿用） |
| **Assignment** | **Router** | 每次派发 / 重试 / 改派；新代际生效即作废旧代际（fencing） |
| 任务域 | 执行节点 daemon | 收到任务信封后，一 Assignment 一域（一任务一域是硬约束） |

**通用纪律：智能住在「决定」里；对象创建永远是「动作」。** 五个对象的创建动作没有一个需要 agent——它们是确定性簿记（轨道登记去重、thread 签发归属、Ticket 照接受决定写记录、Assignment 照派发决定写记录、任务域照信封建环境）。需要智能的是创建（或处置）**之前的决定**：thread 的合并（三级：引用自动 / 推断由 Router 提议并带复核标记 / 人工兜底，4.2；结论 62 已修正）；Ticket 的**接受决定**即准入链的 Eval——这件事值不值得办、Mandate 凭哪次审批、订阅哪些轨道，全链路第一个真正的智能判断（确定性前置过滤先挡噪音，粗筛可小模型，接受/拒绝裁决用强模型或人；人直接下的指令走同一接受决策）。这一模式与 Watchdog（绊线=规则、纠偏=模型）、Router（粗路由=轻模型、裁决=强模型或人）同构：便宜的全量动作 + 昂贵的个例决定。

**Ticket 的生命周期**：

```
创建（接受决策：Mandate + 订阅 + 首个 Assignment）
  → 运行（订阅直通收新事件；多代 Assignment；人工提问可挂起）
  → 结束（ended：by = executor | human；outcome ∈ completed | merged | closed | dropped | stopped；带署名理由）
```

- **Ticket 没有销毁**：结束是终止态，但记录**永久保留**——Ticket 本身就是台账的一部分。会真正销毁的是它下面的任务域（6.2 节）。
- Ticket 结束的判定在编排层；其订阅的 thread 不因 Ticket 结束而受影响。两者关系是**双向多对多、且不对称**：一条 thread 可被多个 Ticket 订阅（同一件事被分成几件活来办），一个 Ticket 也可订阅多条 thread（一件活涉及几件事）；不对称在于**先有 thread 后有 Ticket**——thread 独立存在、不属于任何 Ticket，Ticket 只是订阅它。

**五个对象之间的基数（方向一律写作「前者 : 后者」）**：

| 关系 | 基数 | 形成方式 |
| --- | --- | --- |
| 来源轨道 : thread | 创建时 1:1，合并后 **N:1** | 登记确定性建立；合并三级（引用自动 / 推断带复核 / 人工兜底，4.2） |
| thread : Ticket | **M:N 不对称**（先 thread 后 Ticket） | Ticket 创建时按接受决定订阅 |
| Ticket : Assignment | **1:N** | 每次派发/重试/改派新增一个，同时至多一个活跃 |
| Assignment : 任务域 | **1:1** | 一任务一域（硬约束）；域内可跑多个会话 |

**TL;DR：订阅对应关系的智能判断在「分组」与「接受」（原型里就是 main Session/Router 做的），订阅本身是接受决定的机械后果（`tickets.ts create()` 按接受批的 triggerIds 机械订阅，零判断），事后补订需要消息明确指向某个 Ticket；它可扩展，因为候选集由确定性机制预构造（引用 + 同现 + 实体窗），上下文有界且不随全库增长，错订可逆、漏订可补。** 以下展开。

**「归并」优先发生在订阅层，不动 thread。** 「邮件、GitHub、Slack 谈同一件事」的默认解法不是合并 thread，而是**开一个订阅多条 thread 的 Ticket**（原型 `Tickets.create` 即如此：把 Eval 那批 trigger 涉及的 threads 全部订阅；新增订阅也是既有能力）。效果：Worker 在一个工单里看全三路输入（订阅直通），thread 一字不改、可逆（退订即可）、错「合」代价限定在单个 Ticket 内——结论 62 担心的「两个事项被混在一起」在此不发生，因为没有被混的对象。**thread 级合并只留给身份需要超越单个工单的场景**：thread 锚定业务实例（FlowCatalog）、长期线索跨多 Ticket、报表口径——此时才走 4.2 的三级合并（引用自动 / 推断带复核 / 人工兜底）。分工：订阅归并管「把活干全」，身份合并管「事项同一」。跨租户只有后者被禁止（结论 41/67），前者配合引用机制是唯一通路。**订阅对应关系的判断是可扩展的，因为候选集是确定性预构造的**：原型里订阅本身是接受决定的机械后果（`tickets.ts create()` 按接受批的 triggerIds 机械订阅），判断在「哪些 trigger 归成一批 Eval」与「接受与否」；企业版同样让 agent **只在个位数候选集中确认对应关系，从不在全库中搜索**——候选集三个来源全部零模型成本：显式引用解析（覆盖企业实践的大多数）、同现记录（`correlated`，到达时即记）、同实体+时间窗。上下文模板因此有界（thread 时间线元数据 + 候选摘要 + 先例，数千 token，**不随全库 thread 数增长**），判断成本 ∝ 候选集而非数据量。安全网使「不看全」成立：漏订可补（后续事件显式指向即 attach/follow，原型已有）、错订可逆（退订，thread 不动）、系统性误判由 Watchdog 抽检与推断合并复核标记捕捉——**可逆性决定授权粒度：错合并不可逆故闸门严，错订阅可逆故可放手**。

**Assignment 的生命周期**：`pending → running → ended`（带 report 与摘要）。两条纪律：

1. **中断不是失败**（结论 48）：节点沉默或失联转「中断待恢复」；中心改派 = 新 Assignment（新代际），旧代际迟到结果一律作废。
2. **同一时刻一个活跃代际**：Assignment 之间靠代际 fencing 排序；跨节点改派后，节点的「先对账后接派」以 Assignment 归属为准。

### 6.5 租户冻结

租户被判定无效后，它的编排事实不会被立即抹除，而是进入冻结（结论 46）：

- **业务写入停止**：不再派发、不再新建 thread、不再新建任务（结论 46）。
- **在途任务不中断**：已经派发出去的任务跑完并上报（结论 47）。外部副作用一旦产生就收不回，中断只会让对账差集变大。上报照收——它是把已有的工作在账上关掉，不是产生新工作；拒收只会让在途集合永远清不空。
- **对账写入继续**：核实结论、人工裁定、超时升级仍然可以写（结论 56）。冻结要停的是「产生新工作」，清点旧工作恰恰是冻结之后最该做的事。
- **业务动作延后**：冻结期间人可以下结论，但由结论派生的业务动作排队到解冻之后，或交给 BOS 的流程（结论 58）。「解冻」指 `TenantDirectory` 重新判定该租户有效；本文不定义解冻的其他条件，也不假设它一定发生。
- **历史随保留期清除**：对账历史与人工裁定不单独设期限，与业务事实一同清除（结论 59）——它们的意义是解释业务事实，事实已清而记录孤存，既无解释力又是合规负担。

对账写入的表达能力被严格限定：只能做固定迁移，只能写结论、依据与署名，不能携带业务字段（结论 57）。否则对账通道就会变成绕过冻结的后门。

## 7. 隔离与信任

隔离不是一个词，而是三层，必须分别满足（三层的划分来自既有研究材料；本项目如何承担见下表）：

| 层次 | 内容 | 本项目如何满足 |
| --- | --- | --- |
| **故障域** | 一个任务崩溃或耗尽资源，不拖垮其他任务 | 每个任务一个任务域；节点在容量不足时降级而不是被强行塞满 |
| **文件与凭据边界** | 一个任务读不到另一个任务的代码与凭据 | 任务域独立目录；凭据随任务注入、随任务销毁 |
| **租户边界** | 一个租户的任务不能借用另一个租户的身份或数据 | 编排存储按租户划分；租户凭证带过期；引用跨租户时只给指针 |

### 7.1 执行节点属于人

执行节点（员工机器上的常驻组件）**属于人，不属于租户**（结论 21）。一台机器一个节点，可以同时服务多个租户；因此租户边界不能由「归属哪个租户」来保证，只能由节点内部的任务域隔离来保证。

节点不是中心远程拉起的：员工机器在 NAT 之后、只能出站，节点必须自己主动连上来（第 11 章「连接方向」）；中心「拉起」的对象是任务域里的执行环境（4.5 节），不是节点本身。

取舍很明确：把节点绑死到租户上，隔离最强，但员工要为每个团队各跑一个常驻组件——这违背了借用员工环境的本意。

### 7.2 容量是观测值

节点上报的剩余容量必须是可核实的实测值，不能由节点自行声明可接纳量（结论 27）。调度必须建立在可核实的数字上，否则它就是在用被调度者的主观陈述做决策。节点的存在、在线状态与这些观测容量，和派发、在途记录一起保存在编排存储里（结论 31、34）——「节点注册表」不是另一个系统，只是这份事实的查询视图。

节点只陈述容量事实；延迟、改派、降级由 **Router** 依优先级决定，不在节点（结论 26）。这里的「优先级」属于组织决定：**Router 的调度顺序不构成业务优先级**，「模型报告完成」也不等于业务验收（结论 16）。

### 7.3 掉线与恢复

节点离线时，其上正在执行的任务被判为「中断待恢复」，而不是失败（结论 28）。超时窗口之后，调度可以改派；原节点若回来，其迟到的结果被代际作废，不能与新执行同时写入。

节点重新上线时，必须先对账、后接派（结论 29）：先上报离线期的在途任务与已产生的外部副作用；编排层确认之后，它才接受新派发。

### 7.4 调用身份与授权是两回事

一次外部调用要通过的检查不是一道，而是几道（结论 15）：

- **调用身份**回答「谁在调」——是编排层的调度角色，还是某个具体任务；
- **Mandate（任务授权）**回答「凭什么调」——这次工作是被什么依据允许的；
- **工具授权**回答「能调到什么」——调用方在这个环境里实际能触及哪些能力。

三者不可合并成一个权限字段。此外，事件发送者、组织规则与操作系统权限仍需分别审查。UHP（Unified Harness Protocol，一个把「产品如何驱动异构 harness」做成开放协议的项目）用「配置好的 harness」（harness 基类 + 模型、提示词、工具限制、skills 与预算，带服务端签发 id）来指向「哪一个 agent、以什么配置」，可供调用身份建模参考。

### 7.5 凭据不进模型上下文

agent 只调用**能力**（建合并请求、读问题单、更新讨论），不持有凭据。凭据由适配器或执行节点在调用发生时注入（结论 78）。这与「轨道只存引用」「知识正文留在来源侧」是同一条原则：agent 接触语义，不接触秘密。UHP 的安全章把同一原则写成硬要求：agent 工具不该读到 provider 凭据；必须下发时用短时、单会话、可独立吊销的凭据。

### 7.6 单写者

编排层可以由多个副本提供，但同一租户的编排存储在同一时刻只有一个写者（结论 32）。写权通过条件写入与代际取得，不引入独立的锁服务（结论 33）：冲突即拒绝，重读重试，而不是在另一个可能失效的系统上排他。

### 7.7 三个角色各自的约束

**异构 agent 的信任分级无法外包给被调用方**——BOS 不知道、也不该知道调用方是 Router 还是某个 Worker，因此调用身份是本项目必须自己解决的第一件事，在推导次序上先于编排事实（结论 13）。原型里有 `ActorRef`（来源、标识），但那记的是**事件发送者**在来源侧的身份，不是**调用方角色**的身份：前者答「谁提了这件事」，后者答「哪个 agent 在调这个能力」。它因此没并进第 10.3 节那张清单——它不新增一个承载实体，而是给已有的每一次调用补上一个可判定的身份。

**Watchdog 判断「有没有进展」只能读编排事实，不问 agent**：异构 agent 各说各话，编排事实是唯一可观察的共同事实面（结论 77）。读台账的形态分两层（见 §11）：绊线是确定性规则，裁决是一次 one-shot 强模型调用——都不需要会话。

**Router 的模型调用成本与执行成本同记在租户账上**，这样「要不要给 Router 换更强的模型」与「要不要多派 Worker」共用同一预算（结论 81）。

## 8. 人工介入

人工介入不是一个功能，而是 BYOM 能成立的前提（结论 3）。它分布在三层，各司其职（结论 79）：

| 层次 | 人能做什么 |
| --- | --- |
| **执行节点层** | 看见在自己机器上正在跑什么；在必要时接管 |
| **编排层** | 改派、停止、把一条线索交给别人；在冻结期间下对账结论 |
| **业务系统层** | 审批、验收、退回——这些属于 BOS 的流程，不由编排层代劳 |

三层缺一不可。如果介入只存在于编排层，员工就看不见自己机器上的实际执行，「看得见、接得住」就只剩一半；如果介入只存在于业务系统层，同样看不到执行现场。

人工介入在技术上还有一个前提：**执行调用必须是非阻塞的**。如果一次工具调用会一直占着，直到做完才返回，那么「随时介入」在架构上就不可能（结论 19）。

## 9. 知识生产线

认知事实的写入不是「agent 写着写着就存进去了」，而是一条有角色、有确认、有历史的链路。

### 9.1 提案

agent 只能提交**提案**：一份草案、它依据的证据、以及它建议由谁负责（结论 73）。提案本身也是一条可追溯的记录。

提案不会直接进入检索面。未确认的内容一旦可被检索，就会参与后续的决定（结论 73）。

提案的提交与入库都不经过 KnowledgeQuery（5.2 节说它只读）；那条通道只做查询。提案走哪一个入口属于实现细节，本设计不展开。

### 9.2 确认

提案必须由**人**确认后才能入库。责任人是这条知识的**责任角色**，不是它的写入者（结论 71）；责任角色必须由人担任（结论 72）。agent 不能自己改写制度事实或认知事实，只能提请、由人确认（结论 5）。agent 可以起草、可以提请，但不能为组织承担知识的责任，也无权推翻。

### 9.3 驳回与推翻

被驳回的提案永久保留，连同驳回理由，但不进入检索面，只能由人显式查阅（结论 74）。「我们曾经以为这条成立、后来被否决」本身是组织知识。

一条知识被推翻时，此前基于它做出的决定**保持原样**，另记一条溯源：「它当时依据 X，X 已于某时刻被推翻」（结论 75）。历史决定在当时是合规的，重写它就抹掉了「当时是否尽责」这条最重要的审计信息。

至于「现在还能不能继续」，由知识责任人发起（结论 76）。系统只把这条声明挂到受影响的决定上，不自行扫描、不自行判断哪些决定还成立——那又回到「事实认定」与「业务决定」混同的老问题上，也就是 2.3 节那条防越界规则。

## 10. 与原型的关系

本设计借鉴公开的 DSH Super-Agent 原型与相关文章，但**继承逐项挑选**，不是整体照搬。

### 10.1 直接照抄的七项

下列机制在原型中已经被实现过，且其语义不因本设计的三条要求（来源更广、agent 异构、进程隔离）而改变，因此直接继承（结论 83、84）：

| 机制 | 内容 |
| --- | --- |
| 副作用队列 | 反复失败的任务按指数退避重排；被明确推迟的任务不计失败；同一任务重复入队时替换内容但保留队列位置 |
| 授权与能力的区分 | 「这次工作凭什么被允许」与「这个 agent 能调用什么」分开判定 |
| 线索订阅与扇出 | 一条线索上的新事件，只送给订阅了它的任务，不经过 Router 转发 |
| 停止、恢复与唤醒 | 人停止一条工作会撤销其授权；中断的执行会被重新排队；人的后续消息可以让已结束的工作在复查授权后恢复 |
| 评估去抖与超时 | 同一线索上的多个待评估事件合并为一次评估；超时重排有上限；倒计时从候选送到评估者时开始；暂停期间顺延 |
| 策略版本复查 | 授权依据里记着当时的策略版本；策略变化时重新评估，而不是沿用旧结论 |
| 幂等与回执 | 每条对外消息先写回执再入队；重复的消息标识被忽略；不可达的渠道被终结，不做无限重试 |

「照抄」不等于「不加核对」。这七项在原型里跑在单进程、宽松权限之下；放进本设计后，每一条都要按租户划分与隔离要求重新审视一遍，才谈得上实现。

### 10.2 明确不继承的

- **单进程、单数据库、单目录锁的单写者模型**（结论 4）。原型把「一个进程」当作隔离手段，本设计要求角色可以跨进程、甚至不属于同一个运行时。
- **把一切会话放在同一个宽松权限下的做法**（结论 22）。执行节点属于人，隔离落实在任务域与凭据边界上。
- **由来源决定线索标识**。本设计中标识由本项目签发（结论 60）。
- **把派生态存进库里**。派生状态一律现算、不落库——这一点照抄原型（结论 83）。

### 10.3 原型没有、本项目必须新增的

- **执行节点**：故障域、凭据边界、租户边界的承担者（结论 14）。
- **对账**：外部副作用的三态语义、核实、转人工与人工裁定的留痕（第 6.3 节）。
- **编排事实与编排存储**：以 thread 为锚的四类事实，按租户划分的独立存储（第 4 章）。

## 11. 仍未回答的问题

以下四项**尚无正式裁决**，但都已有倾向与展开（见各项后的「已形成的倾向」段）；如实记录，不把倾向说成裁决。

**其一，四个「会话」如何对齐。** 助手会话、agent 实例、业务实例、一次问答，四个主语同时存在于系统中。BlueCortex 又添一层：它的 `mem_sessions` 表记录的不是活的会话，而是**被观察过的助手会话的档案**——以来源侧的会话 id 为键。第 5.3 节的接口把这个问题挡在了适配器内，上层不必先解决它——但挡开不等于解决。在某些场景下（例如跨系统追踪一次完整的工作），仍然需要明确主语。

**其二，本项目与 BOS 的接缝细节。** 调用形态已经确定（第 3.3 节、第 7.4 节），但「Mandate（任务授权）是本项目自己的，还是从 BOS 的授权派生」尚未定论。这个问题决定授权链落在哪一侧，需要与 BOS 的接口细节一起考虑。

**已形成的倾向（非正式裁决）**：Mandate 基本由本项目自持，记录里带「派生自哪个 BOS 审批」的不透明引用。依据是两层语义本就不同：BOS 沉淀治理知识与治理制度——只对**重复且标准化**的流程建模并运行流程模型的实例（非标准化的、一次性的协作不建模不进 BOS），流程的任务节点上 agent 可以参与或提示用户介入——它回答「这类事该不该做、按什么流程做」；Mandate 是运行侧记录，回答「这一次开工凭的是哪次审批」。倾向主系统自持还有一条工程理由：编排层不依赖 BOS 在线可用。正式裁决仍待与 BOS 的接口细节一起确认。

**其三，多层审查如何落到具体设计里。** 事件发送者、组织规则、Mandate、调用身份、工具授权、操作系统权限这六项，每一项由谁判定、在哪个系统里留下记录，还有待逐层展开（结论 15 只确立了「必须分开」，没有给出层数）。

**其四，异构 agent 之间怎么通信。** Router、Worker、Watchdog 若是不同厂商、不同运行时的 agent，它们之间要互相交代「谁在等谁、进展如何、发现了什么」，就必须有一条通道。异构意味着这条通道只能是消息与状态，不能靠共享内存。原型里这不是问题：Router 与 Worker 是同一宿主进程内的会话，`relay` 与 `notice` 都是内存动作（原型没有独立的 Watchdog 角色）。跨进程、跨厂商之后通道走哪条——消息队列、双方共同实现的协议、还是经编排层转述——阶段一的最小解是**经编排层中转**（复用 C1/C2 通路），正式形态待裁决。

**已形成的倾向（非正式裁决）：Router 与 Watchdog 都在主系统侧（编排层）运行，不进执行节点；执行节点上的 daemon 不是三角色中的任何一个。** 依据三条：① 输入在哪，判断就在哪——Watchdog 只读编排事实（结论 77），台账单写者在中心；节点只持执行态，把 Watchdog 放节点上要么复制台账（破坏单写者）、要么依据非权威进度流做裁决（结论 77 禁止）。② 视野决定职责——Router 的改派要全局容量与优先级（结论 26），节点只看得见自己。③ 信任与可达性——节点在 NAT 之后不可达，且 Router 持 Mandate 与准入链，员工机器不能承载。特殊对待上，两者是系统里第一批「持有特权的 agent」：Watchdog 分两层——**确定性绊线**（规则读台账：超时/无事件/心跳断 → 触发，防漏报、可审计）+ **绊线触发后的纠偏判断走 one-shot 强模型调用**（不是会话、不是常驻 agent；可以上强模型；外部经验「弱模型纠不动偏」；DS 团队「小模型够用」只采纳检测半句）；Router 分级——小模型做高频粗路由（成本记租户账，结论 81），准入裁决与复杂改派留给强模型或人；两者的派发/改派动作落台账带署名（与 C8 人工介入同款纪律），其自身的模型调用同样走准入。

**「项目经理/裁决者」放在哪里（同一倾向的展开）。** 这个词其实是四个职能的打包：进度监督、偏差判断、纠偏执行、团队内协调。三个候选不是三选一，而是三个尺度，各覆盖一部分：**节点内组队 + 内置 PM** 覆盖「团队内协调」——它契合不透明协作原则、离线可自治，但不能替代项目级监理，硬理由是监督者不得与被监督者同生灭（节点崩/断网时最需要监理）、它看不到全局、且 Driver B 的节点内部是员工自己的 agent（我们无权规定其内部组队），**故凡是必须保证存在的监督只能放中心侧**；**Router 承担裁决** 不推荐——Router 在一次派发的热路径上，监督是周期性慢回路（节奏错配、故障爆炸半径放大），且判决与执行同体会破坏署名审计（把结论 77「观察归观察」延伸为「判决与执行分离」）；**Watchdog 承担** 是推荐落点，与外部团队经验一致。由此形成三层：L0 节点内 PM（可选、对中心不透明、中/弱模型）→ L1 Watchdog 监理（中心侧、强模型、产出署名「裁决建议」）→ L2 Router 执行者（中心侧、轻模型、执行改派/升级并署名）。两条纪律：判断与执行分离；监督者不与监督对象同生灭、不依赖节点在线。

**数量问题（「多少个 Router / Watchdog」）：按分片回答，且按「决定率」而非「事件率」回答。** 订阅直通、确定性前置过滤、引用合并自动、登记零判断意味着事件流大部分不经过 Router——Router 只吃「决定流」（新线索处置、Eval、派发）。四个独立扩容旋钮：准入链按事件率（无状态 worker 池）、Router 按决定率、绊线按事件率（读台账）、裁决按异常数。Router 内部有两个串行化域：**处置按 `thread_id` 哈希、派发按 `ticket_id` 哈希**（thread:Ticket 是 M:N，不能共用一个分片键），各自哈希到同一副本池（副本携带滚动 session 状态、按 session 粘住——见下段混合设计；决定本身仍可从台账重算，副本崩溃只丢节奏不丢账）；跨分片订阅直通靠 `event_id` 幂等 + 至少一次投递。多租户部署单元是 **cell**（一组副本服务一组租户，分片键带租户前缀，大租户可独占）——比「每租户一套进程」现实。扩容指标各归各：准入看事件率与登记延迟（永不降级）、Router 看决定延迟 P99（恶化时新事项排队、直通照常——业务无感）、Eval 看等待时长（闸门调级 = 用精确率换吞吐）、裁决看异常积压（缺席不丢账，恢复后批量处理）。不变式：编排存储单写者；每 thread 处置串行、每 Ticket 派发串行；跨分片幂等；租户间零共享。PoC 单 cell；扩容四道防线：准入/绊线 worker → Router 副本 → Eval 闸门调级 → 多 cell。**基数澄清（防误读）**：逻辑 Router = 每租户一个（身份 = 角色 × session 状态），副本是同一逻辑 Router 池化的多只手，不是多个 Router；Watchdog **不是每 Ticket 一个**——绊线是共享 worker 池（每个 worker 同时盯全部 Ticket 的台账事实），裁决是每租户一份监理职责（案卷按 Ticket 组织，一次开一卷——注意「单案裁决」本身不是长命会话，见下段判断/会话分工），抽检是每租户定时巡检。**Ticket 是监督的记账单位，不是监督者的编制单位**——若每 Ticket 一个监理，成本随工单数线性爆炸，违背「便宜的全量感知 + 昂贵的个例判断」。**「池化」的准确含义**：池的是**承载 session 的服务进程（执行槽位）**，不是 session 本身——Worker 类 harness session（员工的 claude/codex）与对话 1:1 绑定、不池化（单执行路径模型）；Router session 同样与对话 1:1，但它是持久化实体（`dsh-session-persistence`），粘住池中某个槽位跑（affinity），槽位崩溃即在另一槽位 resume——像浏览器标签页与浏览器进程：标签页 1:1，进程可池化、可替换，标签页不死。**「一个进程一个会话」只对 CLI 交互模式成立**；SDK/宿主模式下多路复用发生在宿主层，每个会话底层仍是隔离执行单元 + 持久化：Codex TS SDK 一个宿主持多个 Thread（每回合起子进程，thread ID 续状态）；Claude Agent SDK 并发多个 `query()`（各起 CLI 子进程，`session_id` resume/fork）；DSH 最彻底——宿主 Cordis context 直接管理复数 harness session（main + 每个 Ticket 的 worker，各带 preset 与持久化）。共同规律：**没人把多个会话挤进一个上下文窗口**；会话连续性锚在持久化 + resume 上，不锚在长驻进程上——所以即使换用「每回合子进程」模型（Codex SDK 式），池化架构一行不改。

**Session 的维护（LLM 无状态 → 记忆分两种角色：投递管正确性，session 管节奏；上下文机制不自建）**：**上下文组装机制是 harness 的本职，我们一行不写**——窗口管理、压缩/摘要、持久化与 resume、消息信封、易变段（策略/聚合表）的每请求重新生成，成熟 harness 全部已做（原型证据：`docs/004-prompts.md` 59 行 Policy 段每请求重新生成、61 行消息以内联 Trigger 卡送达且截断内容只给资源指针、95 行 session 每请求读最新版本；`docs/006-deployment.md` 的 `dsh-session-persistence`）。这与「流程引擎一行不写」（结论 7）同构：**在别人已经做重的地方不再做重**。我们自建的只有三样，全是「投递什么」与「记账」，不是「怎么装」：①**投递内容**——候选集卡片（引用+同现+实体窗预构造）、容量/技能聚合表、异常案卷，作为消息或工具结果进入 session；②**台账读取工具**（MCP，等价原型的 bounded reads）；③**署名与快照记账**（决定落台账带 session 身份与快照）。"上下文模板"据此降格为「投递内容清单」——它定义喂什么，不定义怎么管理窗口。原型实证了长命 session 可行，而且是**一等持久实体**——DSH 的 main Session 就是 Router（`docs/001-domain.md:80`：评估 Trigger、接受并派发 Ticket、回信都在这一条持续对话里），candidate 卡片主动送达、不等待、空则结束回合；部署文档进一步确认（`docs/006-deployment.md`）：Router 是**命名的 harness preset（`dsh-superagent-router`）**，应用「needs them to **create and resume** its Sessions」——session 由 `dsh-session-persistence` 持久化、跨进程重启 resume（升级手册要求备份 `orchestrator.sqlite`）。也就是说：**原型的 Router session 不是一次调用，是一个有生命周期、可恢复的运行实体**——企业版把它显式化（身份、代际、快照），而不是否认它。它能成立靠三条**去权威化**纪律（`docs/004-prompts.md`）：只路由不做技术决定、路由注 ≤30 词（决定依据永远是卡片上的事实，不是 session 记忆）；Policy 每次模型请求重新注入（制度永远新鲜）；一次路由调用**批量裁决**多个等待候选（长命 session 的独特优势，摊薄模型调用）。企业版据此修正为**混合**：①每租户 Router 一个**滚动、有界**的工作 session（原型形状），承担**沟通**连续性与低延迟——**判断不在会话里做**（判断/会话分工见本节末段）；②**决定的正确性仍来自当场组装的事实**——卡片 + 有界读取 + 引擎校验，审计快照 = 组装的事实，**不含 session 私忆**（「我记得这线索最近很吵」不构成依据）；③批量判断 = 一次 **one-shot 调用**带同串行域的多张候选卡（原型在会话回合内做批量路由，企业版改为 one-shot 批量调用——同效、请求即快照、更可审计）；④session 压缩/换代/换模板 = session 状态变化 = 新身份，走代际 fencing——原型「harness 压缩会丢旧记忆」的隐式行为，在企业版变成显式的身份与代际管理；⑤长命 session 需要 affinity：按 session 粘住副本，session 状态相同才可互换。Router 永不读事件正文（结论 64）与进度流（非权威）——两种记忆的预算都由此成立。超预算的分层摘要（最近 N → 按天/来源聚合计数 → 里程碑事实永不摘要 → 先例检索）实现在**台账读取工具里**（作为工具结果返回给 session），不是自建的窗口压缩器——压缩仍归 harness。Router/Watchdog 的「经验」来自三处，全部确定性可得：台账先例、租户策略（PolicyUpdate 进模板/每次注入）、认知事实（Spring-AI-RAG）——session 与组装上下文都是这些的投影，不是第三份数据。**由此收口：Router/Watchdog 的记忆体系 = 两件套，已足够，不建第三种机制**——①**harness 的上下文/session 管理**（窗口、压缩、resume、消息投递，见上）；②**BlueCortex 外挂记忆**（钩子捕获、跨会话恢复：只要不清理捕获队列，可还原大部份 session 信息——包括 Router/Watchdog 自己的会话连续性）。二者的分工与既有边界完全咬合：记忆答「过去发生过什么」（痕迹与推移，§5.3），台账答「现状与权威」（编排事实，结论 86）——**必须跨进程重启存活的东西（署名决定、派发、对账）只进台账，不依赖记忆**，因为捕获队列可能被清理，而台账单写者可重建。我们对记忆侧的全部投入就是一条薄适配器（S5/CollaborationMemory），这与 4 人版把记忆侧压缩为一条薄线（开发计划 §4.1）互为印证。

**判断与会话的分工（重要修正：既然上下文可以一次性组装给足，单次判断就不需要 agent）**。三层：①**绊线** = 确定性规则代码，无 LLM（「无状态」只在这里成立）；②**单次判断**（单案裁决、粗筛、批量抽检、preferred 打分）= **one-shot LLM 调用**——投递内容一次性给足（案卷/候选集/聚合表），一个请求出结果，**无 session**：请求即快照，审计最干净，身份 = (角色， 清单版本， 模型， 输入快照) 同走 fencing 但更简单；③**会话角色** = harness session（长命、每租户一个、粘槽位、可 resume），**只保留给多回合交互**：Router 的对外沟通面（收消息、回渠道、与人 C8 协商、指向性 attach）、监理的多步调查。原型 main Session 之所以是会话，因为它同时承担判断与沟通两职——harness 里两者天然共存，但概念上必须拆开：「判断」是函数（输入→输出），「会话」是基础设施（承载多回合交互）。此修正的红利：one-shot 判断无会话开销（无滚动上下文、无压缩），模型成本只随判断数线性增长且每次有界；监理用最强模型（「弱模型纠不动偏」）的预算更可控。「Router/Watchdog 是 agent」的准确含义据此修正为：**它们的判断走 one-shot，它们的沟通走会话**。

**Router/Watchdog 的身份 = 角色 × 状态——有会话者（沟通面/调查会话）是 session 状态，one-shot 判断者是 (清单版本, 模型, 输入快照)；都不是进程。** 不同记忆（模板版本 + 策略版本 + 模型标识 + 作用域）的两个实例，即使同进程，也是两个不同的 Router/Watchdog；状态相同的两个副本，即使跨进程，也是同一个。四条纪律：①署名粒度细化到 session 身份（角色 + 租户 + 模板版本 + 策略版本 + 模型 + session 代际），审计与漂移检测按 session 身份分组、不按进程分组；②**session 代际 fencing**（与 Assignment 代际同构）：一个串行域任一时刻只被一个 session 代际服务，模板升级/策略变更/换模型 = 换代际，旧代际在途决定完成或作废（`STALE_SESSION`，同 `STALE_ATTEMPT`），灰度迁移按分片切代际、不得同分片新旧并跑；③副本互换 ⟺ session 状态相同，调度器调度的单位是 (session 状态, 分片) 而非进程，模板迁移开新副本池；④cell 内多租户 = 一个进程里的 N 个逻辑 Router——资源上是效率，身份上必须透明：署名、预算（结论 81）、审计、限流全按租户 Router 身份走。跨代际的裁决建议不直接沿用：重新组装案卷再裁（与「迟到结果作废」同一条逻辑）。**BOS 实例与 agent 的长期共生（补齐最关键的一条回路）**：不是「agent 建完模型就走」，而是 BOS 流程长期运行、跑到节点时**发布事件召唤** agent。目标态回路四步：①BOS 到达任务节点 → 节点事实进 outbox（BOS 内部已有 outbox 模式，延伸到集成边界即可）→ **发布 Trigger 事件**，载荷带节点/业务实例引用 + `required_skills` 键与版本 + 策略版本（**带键不带内容**——技能定义在 BOS 版本化，我们不缓存摘要，结论 85 同精神）；②主系统准入链收到 → 走完全相同的既有链路：登记来源轨道（来源 = `bos:<instance>:<node>`）→ thread（锚业务实例）→ Eval → Ticket → Assignment，Router 按 required_skills + 表现统计 + 容量路由给最合适的执行节点；③**认领（claim）**——BOS 已有的「领取」动作（lease + 代际 fencing）。claim 的**主体**按节点形态分两路（缺口⑦）：Driver A 云端 agent 由 agent 直接经 MCP claim；Driver B 员工节点由 **daemon 以设备身份 + 任务信封代理 claim**（agent 不持 BOS 凭据，倾向待 ADR）——无论哪路，「claim 才是权威授权点」不变；④干活 → MCP「提交结果」+「对账」，回路闭合。**权威设计**：路由不等于授权——②的 Router 指派是建议（编排事实，我方台账），③的 claim 才是真正授权（BOS 侧 lease + fencing 校验）；Router 指错节点不会越权执行。与全程纪律同构：TriggerDisposition 不授予权限、Eval 接受才有 Mandate、claim 才碰真任务——四道门各管一道。**实现双路径**（下游完全一致，只影响时效）：路径 A 目标态 = BOS 补事件发布（outbox 延伸）；路径 B PoC = FlowCatalog 适配器轮询就绪节点、合成同样的内部 Trigger。ADR 判据：节点就绪到 agent 开始的端到端延迟要求（分钟级必须 A；容忍 5–15 分钟则 B 先跑、后升 A 无返工）。三条边界：①**状态权威分离**——BOS 说「这个节点在等」是制度事实，我们说「派给谁、在途、对账」是编排事实；回写只提交结果与副作用，不描述编排。②**跨范围**：组织粒度不必对齐（结论 66），同一业务实例可被多个租户的 thread 各自引用、不合并（结论 67）。③**对账闭环**：副作用涉及 BOS 业务动作时必须走 BOS 对账确认，我们的副作用清单不能替代业务事实（结论 85 同精神）。修正措辞：§11 前文「流程的任务节点上 agent 可以参与或提示用户介入」读起来像补充，实际是**核心交付形态**——BOS 是长期运行的制度机器，agent 是被它召唤的参与者。前一段的 session 身份纪律据此仍成立：异构前提（角色靠消息与状态协作、不共享内存）在 session 层的重新应用——进程边界从来不是身份边界，状态边界才是。

**该回路暴露的八个决策缺口（含倾向，待正式裁决）**：①**BOS↔主系统事件契约未定义**——byomd 契约只覆盖中心↔daemon；倾向建 `bos-event-contract v0.1`（同构 byomd 契约：schema+版本+订阅回放+去重键），node-ready 为第一个事件。②**BOS 来源 Trigger 的 Eval 策略**——模型发布时人已审批，逐节点再 Eval 是双重治理；倾向 BOS 来源 Eval 退化为**确定性直接受**（Mandate 引用「派生自哪个 BOS 模型审批」）——Eval 的定位由此澄清：它是「自由事件的准入」，不是所有事件的必经站。③**Ticket 粒度**——倾向每节点一个 Ticket（工作单元），thread 锚业务实例提供跨节点连续性与报表口径。④**HUMAN_TASK 走不走同链**——倾向走同链：Ticket 不派 Assignment、通知员工助理由人 claim（主动型 agent 的产品亮点），BOS 自有通知留作降级。⑤**无主节点任务**——required 技能无人满足：倾向升级计时器（超阈值升级到人：扩技能/降要求/改派人工），绝不静默降级派给不满足节点。⑥**双侧状态一致性**——迟到提交（BOS lease 已过期）= 对账条目不重试；周期性全量对账（就绪未领节点 vs 我方未决 Ticket 差集 → 补 Trigger）；绊线加漏召探针（节点就绪超 X 分钟无 Ticket）。⑦**Driver B 的 claim 凭据**——倾向 daemon 代理 claim（设备身份+任务信封），agent 不持 BOS 凭据（避免凭据扩散）；Driver A 云端 agent 可直接 MCP claim。⑧**派发形态**——倾向同一任务池、pull 为主（byomd 本就是 PullTask），required 技能作为节点拉取过滤条件，Router 对 BOS 任务只做入池排序优化（决定率旋钮不被事件率绑架），对自由来源仍必须指派。八项中②⑤⑥⑧均可被既有骨架（确定性快速通道/升级到人/对账/pull 池）直接接住——待拍板的是选择，不是发明。

**员工执行节点的参与粒度（授权形状）**：员工对「中心用我电脑」的控制是**四档可自选、每档可设零**——纯手脚（BYOM 嵌套的执行环境，不创建 agent）；**受控 spawn**（模式 1：注册时给 `spawn_policy {max_concurrent, allowed_harness, allowed_models}`，中心按信封 spawn 真 harness 进程，N=0 = 永不创建）；**调度已有**（模式 2：daemon 检测员工已在跑的 agent 会话（Herdr manifest 检测），员工**逐 agent 显式 opt-in**「允许中心调度」，opt-in 的进入可调度容量，其余中心不可见）；不参与。spawn_policy 经注册/配对协商 + `PolicyUpdate` 变更、随时可撤（撤回 → 优雅终止全部 spawn 的 agent，只留移交包）；spawn 只管「能否创建进程」，任务域隔离纪律照旧（不等于授权碰数据）。模式 1 = Driver A 的本地变体（daemon 单路径模型的核心动作），模式 2 = Driver B attach 路径；同一节点可共存，`TaskEnvelope` 指明走哪条路径，两种容量同池竞争、技能/表现统计统一记账。

**技能（skill）作为一等概念（已识别的缺口与倾向）**：现状盘点——BOS 有 `AGENT_TASK` 节点 + 可挂 `AgentDesignDocument`（modelId/Tool/Knowledge/Guardrail/allowedRoles），但那是**装配语义**（指定具体配置），不是技能需求声明；byomd 契约的 `capabilities[]` 是 daemon/机器能力（attach/conpty…），不是 agent 技能；派发只有 `role` 维度，无技能匹配。倾向的四件套：①**设计时**：`AGENT_TASK` 节点增 `required_skills[]`（required/preferred 两级），与 AgentDesign 挂载并列；技能词表 = 租户词表 + 可引用全局词表（治理知识，进 BOS 制度事实、版本化）。②**注册时**：契约 v0.2 候选新增 `SkillReport`——Driver A 技能 = 部署声明的 agent 设计（引用 AgentDesignDocument），Driver B 技能 = 员工自报 + 表现统计。③**匹配**（Router 派发内，两级）：required 缺失 → 硬过滤不派（任务挂起等待或降级派发需人审批，同 capability 缺失规则）；preferred 命中数 + 容量 + 优先级打分择优（纯规则起步，小模型可参与）；派发事实记录命中技能与排除依据（署名可审计）。④**表现记账**：Assignment 完成后按 Ticket 类型回填节点/agent 技能统计（完成次数、有无异常）——「最符合要求」的证据 = 声明 + 表现，与 Watchdog 读台账、Router 看容量同源；派发投递清单增「候选节点技能/表现聚合表」（与容量聚合表并列，只有数字不有个案）。

**Watchdog 这个词指什么（最终定义）**：指**监督职责本身**（盯进展、发现偏差、产出裁决建议）——不是「一个模块」，也不是「一个有会话的 agent」。与 Router 同构：两个角色词都是**职位名称，不是员工**，在不同时刻上岗的是不同实现形态——绊线 = 编排服务里的规则代码；单案裁决与批量抽检 = one-shot LLM 调用（无 session）；多步调查 = harness session（只有这种时候才有会话）；裁决建议的执行 = Router（判决与执行分离）。实现形态的选择纪律与成本纪律同一条：能用规则不上模型、能用 one-shot 不开会话、只有多步调查才开会话。Router 按此定义同理：「Router 是 agent」的准确说法是「Router 的职责由规则、one-shot 调用与沟通会话共同填充」。

**措辞澄清：绊线与裁决是同一个 Watchdog 的两个机制，不是两个角色**——角色始终只有 Router / Worker / Watchdog 三个。必须两层的理由：①盯是高频全量、裁决是低频个例，让强模型读每条事件是用最贵的注意力干最便宜的过滤（同「确定性前置过滤」结论 18 的成本纪律）；②活性检测是确定性事实（心跳断/超时无事件），交给模型只引入幻觉空间，且规则触发可复现可署名（Herdr `DetectionExplain` 同款纪律）；③与 C8「规则触发 + 人判断」、Router「粗路由 + 强仲裁」是同一模式：便宜的全量感知 + 昂贵的个例判断。**已知缺口**：绊线只抓已知模式的偏差——由判断层的**周期性抽检**补（监理职责的低频巡检——one-shot 批量调用，不开会话；优先抽最老/最长/异常最多的 Ticket，不依赖绊线触发），两层由此闭环：感知层管已知模式，判断层管已知 + 未知。**裁决的执行纪律**：L2 Router 可以**拒绝执行** L1 的裁决建议——拒绝必须记录异议并署名（改派确有误判时，如长任务被误报卡死），异议直接升级到人（C8），**不得在两个 agent 之间循环争论**；拒绝与执行都是编排事实，同等级落台账。

**thread 的创建不经过 Router（同一倾向的补充）**：先分清两个对象——**来源轨道**（§4.2，来源侧一条会话流的指针，`来源:id`，原型 `Thread` 对应的其实是它，原型把名字用松了）与 **thread**（§4.1，本项目生成 id、可挂多条来源轨道的协作线索）。登记分两步：**轨道登记是确定性的**——事件级幂等去重（按 `(来源, 事件标识)` 等值丢弃）+ 轨道级 get-or-create（对 track key 字典等值查找，零判断、零模型成本）；**thread 锚定随之确定**（轨道首次登记时同步建 thread，创建时刻严格 1:1，id 由本项目生成、不派生自 track key，结论 40/60），但合并按信号分级（§4.2 三级：引用合并自动、推断合并 Router 提议高置信自动生效带复核标记、人工兜底）——Router 可**提议归并**（判断这条轨道与某条已有线索是同一件事），引用级归并则是确定性解析， Router 只提议不执行，不改写已写定的归属（结论 41）；归并素材由事件触达时的确定性记录（同次触达的其他轨道键，原型 `correlated`）提供。N:1（多轨一索）是合并后天形成的，不是登记时的判断。「多轨道归并到一件事」正是需要智能的一步，也是 thread id 必须自生成的原因：它表达归并判断的结果，来源标识表达不了。两者分离的三条理由：入口是咽喉，洪峰时不能等 agent 判断（否则最忙时停摆）；归属事实「写定后不可变」只能来自确定性登记；故障域分离（Router 挂了入口照常收件，线索不丢）。分片路径随之分开：入口按租户进准入链 → 登记后事件落 thread 队列（按哈希）→ Router 副本消费——不存在「未分片的 thread 没人管」的窗口。

一个可参照的项目是 HarnessRouter 与它的 Unified Harness Protocol（下称 UHP）。它把「产品如何驱动一个异构 harness」做成了开放协议，对本问题有五点启发，但都只是**候选**：

- **协议是分层的，不是一揽子，而且是互补而非竞争。** UHP 是**调用方与 UHP Server** 之间跑一个任务的契约（任务、会话、流式、文件、结果）；**Server 内部怎么启动 harness 不在协议范围内**——容器、子进程、队列、远端 worker 都属于实现，明文禁止泄漏到线上格式里。**agent ↔ agent 的协作走 A2A**（Agent2Agent Protocol）；MCP 管「agent ↔ 工具与数据」；ACP（Agent Client Protocol）管「编辑器 ↔ 编码 agent」。UHP 原文说它与 A2A 互补：UHP 是调用方驱动 harness 的契约，A2A 是 agent 之间对等互通协议，两段边界不同，可能同时需要。因此 Router/Worker/Watchdog 的互通未必需要发明新协议。
- **委托与扇出可以靠「重复同一个契约」搭出来。** UHP 把这种组合命名为 H2H（Harness-to-Harness）：协调方反复调用同一个契约去启动不同 harness，委派与并行 fan-out 就搭出来了；协调住在调用方，而契约本身不变。这与本项目「编排层持有协调、agent 只被驱动」的分工同向。
- **agent 之间的互相发现还没有现成答案。** UHP 的 harness 目录（`/v1/harnesses`）是按用户权限隔离的能力清单，不是跨 agent 注册中心；A2A 能力发现是候选，或者另建一份 agent 注册表。这本身是本问题的子问题：Router、Worker、Watchdog 怎么知道彼此存在。
- **UHP 允许 client 是「另一个 agent」。** 它把 client 定义为「想要把工作做掉的应用：产品后端、CLI、CI 任务、或另一个 agent」。也就是说一个 agent 可以像产品一样去驱动另一个 harness。
- **交换单位是一次任务（job），不是一次模型回应（completion）。** 模型接口给一次回合，UHP 给一次任务：活儿进去，agent 用自带的工具与会话做，结果和工件出来。这与本项目的 thread / 任务域语义同向。

一句话收束这条边界：**UHP 覆盖「调用方如何运行并观察一个 harness 任务」，不覆盖「多个 agent 如何发现、寻址、互相发消息、组播与协调」**。委派、扇出、聚合、失败策略都在调用方；UHP 没有 delegate 原语，也没有父子任务或回复路由。

已确定的仍是那一点：**编排事实是它们唯一共享的事实面**（结论 77）。通道怎么定、彼此怎么发现，都留作待讨论。

**它能提供多少、不能提供什么。** 按「规范里有没有、实现里有没有」两条线逐项算过之后，账目大致是三栏。

- **能直接用的**：驱动的契约形状（任务进、事件流出、文件与结果出、可取消）——即下面 11.2 的 C1/C4/C7 候选；**每 harness 一个驱动器的工程范式**——每回合起一个子进程，逐行读它的标准输出，取消即杀整个进程组，现成有十来个不同 harness 的驱动器；**凭据中继模式**——harness 子进程永远拿不到凭据，模型调用走中继，凭据不进进程、不进环境、不进会话日志，这是「能力即接口」的一个已落地实现，比「不进模型上下文」更强；控制面的租约与 fencing 实现；以及可直接抄的安全规则（凭据短时、单会话、可独立吊销；对象按调用者隔离、越权一律 404；「两个 agent 共用一个工作目录不是定义良好的状态」）。
- **没有的**：任务域信封——隔离域的创建与销毁是规范明文划出的实现细节，没有任何 API；执行节点与 BYOM 接入模型——它是「一容器一卷」的服务器部署，环境建一次、只读、多会话共享，工作区每回合检查点与恢复，与我们「按任务焚毁」的信任模型相反；节点注册、对账、冻结、移交包也都不在其中。
- **落点**：UHP 的语义是「驱动 harness 的契约」的参考形状；HTTP 只是它跨进程、跨信任边界时的承载。节点内部没有信任边界，用子进程加管道（标准输入输出上的行分隔 JSON）加进程组 kill 就够——它自己的驱动器正是这么做；回环 HTTP 只在整块复用它的现成实现时才值得付代价，且必须照它管理接口的做法加认证，因为回环端口对本机任何进程都是可及的。

以下两小节是第四项的展开：11.1 说明原型为什么不足以回答它，11.2 把可能的通信模式列成提案。它们不是第五、第六个未决项。

### 11.1 原型里的 agent 间通信有多原始

原型不是「没有 agent 间通信」，而是**只有同进程对象调用**。三处证据：

- 投递前按 id 解析出的是**内存对象**：`resolveAgent(sessionId)` 返回同进程内的 Agent（`src/app/sessions.ts:158`）。
- 投递时**按对象身份校验**：`ctx.agents.get(agent.id) !== agent` 就直接抛错（`src/app/delivery.ts:71`）。指针相等在跨进程时无从比较。
- 投递目标是**进程内 inbox**：`agent.inbox.nextTurn` / `nextStep`（`src/app/delivery.ts:74`）；`relay` 与 `notice` 只是 `Effects` 队列里的内存动作（`src/app/sessions.ts:104-105`）。

因此它有三条硬限制，正是跨进程、跨机器要逐条解决的：**寻址靠对象引用而非地址**、**身份靠指针相等而非凭据**、**通道是进程内 inbox 而非可序列化消息**。

### 11.2 跨进程与跨机器需要哪些通信模式（提案，未决）

按已确立的前提推——角色之间只能靠消息与状态（第 0.1 节的「agent 异构」）、员工机器通常在企业网络地址转换（NAT）之后，不能接收入站连接、编排存储单写者——得到九种模式，其中六种必须、三种可选：

| # | 模式 | 语义要求 | 方向 | 必要性 |
| --- | --- | --- | --- | --- |
| C1 | **任务下发** | 至少一次投递 + 幂等键；超时记为「未知」，不记为失败 | 编排层 → 执行节点 | 必须 |
| C2 | **结果上报**（含副作用清单） | 幂等写入；缺清单不算完成 | 执行节点 → 编排层 | 必须 |
| C3 | **容量与心跳** | 观测值、单调序号、陈旧上限 | 执行节点 → 编排层 | 必须 |
| C4 | **进度事件流** | 有序、可续传，**且非权威** | 节点或编排层 → 观察者 | 必须 |
| C5 | **对账查询** | 请求/响应；三态（已确认 / 未发生 / 未知） | 编排层 → 来源适配器 | 必须 |
| C6 | **事实追加与观察** | 只追加、不就地改；读模型由查询得出；消费方重连后按游标续读，不假设「一条不丢」 | 编排层 / 适配器 → 编排存储；观察者只读 | 必须 |
| C7 | **agent 间请求** | 请求/响应 + 关联 id；超时按「未应答」处理，不重试同一 id | Router ↔ Worker / Watchdog | 可选 |
| C8 | **人工介入** | 审批、接管、改派；每次介入留署名记录；裁决只改状态、不直接触发外部动作 | 人 ↔ 三层 | 可选 |
| C9 | **共享工作区** | 文件级、仅限同一任务域；并发写需冲突检测或 CRDT（无冲突复制数据类型），不得静默覆盖 | 参与者 ↔ 工作目录 | 可选 |

对应的技术路线，同样是**提案**：

| 模式 | 首选 | 备选 | 为什么 |
| --- | --- | --- | --- |
| C1 / C2 / C3 | HTTPS + JSON + 幂等键；节点侧 outbox（先落库、后投递的本地待发队列）；节点主动拉取或维持一条**出站**长连接 | 每节点一条队列（NATS / RabbitMQ 这类消息中间件）；或 gRPC（一种二进制 RPC 框架） | 员工机器不能接收入站，只能主动连；节点侧 outbox 让离线不丢 |
| C4 | SSE（HTTP 单向流）+ `Last-Event-ID` 续传 | WebSocket（确需双向时）；gRPC streaming | 易穿代理；与 UHP 的流式模型同形 |
| C5 | HTTP 请求/响应 + 适配器侧回执 | 事件 + 定期对账扫描 | 三态语义要明确回执，不能靠轮询猜 |

> **落地物**：C1/C2/C3/C4/C8 的首个具体化是 byomd 契约 v0.1 初稿——BOS 仓库 `docs/drafts/byomd-contract-v0.1/`（自本文件相对路径 `../../../../wubuku/AI-Native-Business-Operating-System/docs/drafts/byomd-contract-v0.1/`；15 条消息 + JSON Schema + 语义表 + 错误码 + 黄金夹具）。该契约随 ADR-001 定案后升级为唯一真源。
| C6 | 编排存储 + outbox 表，消费方轮询或订阅变更流 | Postgres `LISTEN/NOTIFY`（小规模）；JetStream / Kafka（需回放） | 单写者 + 代际，避免双写与乱序 |
| C7 | A2A（带 Agent Card 发现），或**经编排层中转** | 直接 HTTP + 关联 id | 避免全网状互联；中转复用既有路径 |
| C8 | 管理面板 + BOS 的人审通道 | 消息通知（邮件 / 即时消息）作为提醒 | 审批的权威在 BOS，本项目只把人带到正确的位置 |
| C9 | 任务域内共享目录或对象存储 | CRDT 或 Yjs 仅当需要并发共编 | 共享文件不等于共享授权事实 |

三条约束比选型更重要：

1. **连接方向**：执行节点只出站。要么主动拉任务，要么维持一条它主动建立的长连接；不能要求员工机器开放端口。
2. **节点不直连编排存储**。C2 必须走 API。直连会让「单写者」当场失效。
3. **进度流不是权威**。断线、丢事件都属正常；权威始终是编排事实的查询结果。

**C1 派发的具体形态（提案）。** 把派发拆成「通知」与「内容」两件事：中心沿节点主动建立的出站连接推一条极小的派发通知（首选 SSE，断线按 `Last-Event-ID` 续传），内容由节点回 HTTPS 幂等拉取——通知丢了不要紧，节点下一次心跳或轮询会发现待领的任务；重复收到按任务标识去重。工业先例是 Kubernetes 的 kubelet（节点上常驻的代理）：它主动与控制面建立事件订阅长连接，中心沿这条订阅推事件，状态以节点侧对账为准、幂等去重。**不能用的形态**：要求中心回调员工机器（webhook）的方案——A2A 的 push notification 亦然；HTTP/2 的 Server Push 已废弃。通道本身应按语义抽象（主题化、至少一次、离线保留、幂等、不保证顺序），底层在长连接、消息中间件、轮询之间可替换——MQTT 恰是为「NAT 之后的设备接收命令」发明的，它的「至少一次」投递等级与离线消息保留正合此用，但引入它等于多一个要运维的承载者，故列作备选。

三条不做：**不做全网状 agent 互联**（N 个 agent 两两直连是 N² 条通道与 N² 套身份）；**不拿界面的事件总线冒充 agent 广播**（它推的是执行事件）；**不让节点直连编排库**。

以上全部是提案。通道最终选哪条，仍属未决。

调研中另有两个生产系统可作参照，各有一块与本设计直接同构。其一，**Comma**（AFK-surf，AGPL）：它把「至少一次 + 幂等 + 未知态」的送达语义做成了一套完整的站点协议——任务所在方（host）记每个参与方已答到哪（sent/answered），站点连上后先以 `task.hello` 报到、host 按水位补发——可作 C1/C2 的对照。其二，**OpenMausBot**（Apache 2.0）：它的统一 Assignment 运行时（工作树、逐条重启对账、同一请求只答一次）是编排事实的一份桌面级实现，它的 connector 协议（只出站、一条长连接、控制面只签发任务、箱内无 shell）是 C1 通道的一份桌面级实现，它的审批层还把「问题永不自动回答」与「层级沿委派链只升不降」做成了运行时规则。两个系统都佐证同一件事：**通道与账本可以做到生产级；通用准入链、任务域的焚毁语义与组织级治理，在它们那里都是空位**——与本设计第 1.4 节的判断一致，这三样仍是本设计要自建的部分（两类调研报告的全文见备忘 §11 的索引）。

调研中还有三点不写进设计，但记在这里免得再查一遍。

**其一，命名纪律。** UHP 把同一契约的不同命名（AHP / HAP / HCP / MHP / OHP / H2H）解释成「一个契约的不同侧面」，而不是不同协议，与本项目「接口按语义切分」同源。

**其二，要分清规范与实现。** UHP 规范里确有 `GET /v1/harnesses/{harness_id}/events` 这个按 harness 的实时事件流，但它推送的是执行事件，不是 agent 消息；「协作黑板」（Yjs / Hocuspocus 双向协同，落地为工作区里一个文件）在 HarnessRouter 的 `runner/` 里确有实现，但不在 UHP 规范内，也不是 agent 之间通信原语。读这类材料时，「规范里有没有」与「实现里有没有」是两个问题，不能只查一处就下结论。

**其三，一个印证。** UHP 明确不允许同一 session 并发跑两个任务（`session_busy`），这与本项目「一个任务一个任务域」的取法同向。
